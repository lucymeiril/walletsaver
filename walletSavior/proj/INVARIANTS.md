# INVARIANTS.md — 불변 제약 vs 가변 영역

> **이 문서의 목적**: AI에게 "이것만은 절대 바꾸지 마" vs "이건 자유롭게 바꿔도 돼"를 명확히 구분해주는 가드레일.
> 기획 변경이 잦더라도 불변 제약을 지키면 시스템이 깨지지 않는다.

---

## 1. 절대 불변 (NEVER CHANGE)

이 항목들은 프로젝트의 근간이다. 변경 시 전체 아키텍처가 무너진다.

### 1.1 아키텍처 원칙

| # | 불변 규칙 | 이유 |
|---|-----------|------|
| I-1 | **모든 모듈은 `core/contracts/`의 인터페이스에만 의존** | Zero Coupling, 모듈 교체/삭제 가능 |
| I-2 | **`container.py`만 concrete class를 import** | DI 패턴의 핵심 — 조립 지점 단일화 |
| I-3 | **`core/`에는 구현 코드(비즈니스 로직)를 넣지 않음** | core는 순수 정의 계층 |
| I-4 | **모듈 간 직접 import 금지** (core 제외) | 순환 의존 방지 |
| I-5 | **EventBus로 모듈 간 통신** | 느슨한 결합 유지 |
| I-6 | **플러그인 아키텍처: 폴더 추가/삭제로 기능 추가/제거** | Open-Closed Principle |

### 1.2 데이터 무결성

| # | 불변 규칙 | 이유 |
|---|-----------|------|
| I-7 | **baseline 평균에 핫딜 가격 포함 금지** | "가격 오염" — 핫딜은 비정상 가격이므로 평균을 왜곡 |
| I-8 | **가격 비교 시 속성 태그(냉동/냉장, 국산/수입 등) 필수 고려** | 냉동 삼겹살 vs 냉장 삼겹살은 2~5배 가격 차이 |
| I-9 | **테이블 분리: baseline / discount / hotdeal** | 용도별 데이터 격리로 오염 방지 |
| I-10 | **원본 텍스트(raw_text) 항상 보존** | 사후 디버깅, 파싱 검증, 데이터 복구 |
| I-11 | **DataSource enum으로 데이터 출처 추적** | 어떤 데이터가 어디서 왔는지 항상 알 수 있어야 |

### 1.3 품질 원칙

| # | 불변 규칙 | 이유 |
|---|-----------|------|
| I-12 | **TDD: 테스트 먼저, 구현 나중** | 구조적 품질 보장 |
| I-13 | **에러 발생 시 ERROR_LOG.md에 기록** | 같은 실수 반복 방지, AI 학습 |
| I-14 | **모든 함수에 타입 힌트** | AI가 코드를 정확히 이해하고 수정 |
| I-15 | **Pydantic 모델은 `core/models.py`에서 중앙 관리** | 모델 산재 방지, 일관성 |

### 1.4 기술 스택 고정

| # | 불변 규칙 | 변경 비용이 너무 큰 이유 |
|---|-----------|------------------------|
| I-16 | **Python 3.13** | 모든 코드, 테스트, 의존성이 Python 기반 |
| I-17 | **PostgreSQL** | 스키마 설계 완료, JSONB 활용 |
| I-18 | **Pydantic v2** | 전체 모델 체계 의존 |
| I-19 | **pytest** | 64개 기존 테스트 + fixture 체계 |
| I-20 | **FastAPI** | async, Pydantic 통합, OpenAPI 자동 생성 |

## 2. 변경 가능 (CHANGEABLE)

이 항목들은 기획 변경에 따라 자유롭게 수정 가능. 불변 제약만 지키면 된다.

### 2.1 크롤링 대상

| 항목 | 변경 가능 범위 |
|------|---------------|
| 크롤러 타겟 사이트 | 추가/삭제/교체 자유 (플러그인 폴더만 추가/제거) |
| CSS 셀렉터 | 사이트 구조 변경 시 업데이트 필요 (selectors.py) |
| 크롤링 주기 | cron 표현식으로 자유 변경 |
| 전략 순서/구성 | CrawlerInfo.strategies로 크롤러별 지정 가능 |
| API 키 | .env로 관리, 교체 자유 |

### 2.2 프론트엔드

| 항목 | 변경 가능 범위 |
|------|---------------|
| UI 디자인/레이아웃 | 완전히 자유 (백엔드와 독립) |
| 페이지 구성 | 라우트 추가/삭제/변경 자유 |
| 차트 종류 | Recharts 내에서 자유 |
| CSS 스타일 | CSS Modules 규칙만 준수 |
| 컴포넌트 구조 | 자유 (common/domain 구분 권장) |

### 2.3 데이터 관련

| 항목 | 변경 가능 범위 | 주의사항 |
|------|---------------|----------|
| 카테고리 트리 | 노드 추가/삭제 자유 | KAMIS 기준 유지 권장 |
| 속성 태그 | 키/값 추가 자유 | AttrKeys에 상수 정의 필요 |
| 레시피 목록 | 추가/삭제 자유 | Ingredient 모델 준수 |
| 가격 등급 임계값 | 70/85/105% 비율 조정 가능 | statistics.py의 determine_tier |
| 커뮤니티 검증 임계값 | 20/70/120% 비율 조정 가능 | verification.py |

### 2.4 API

| 항목 | 변경 가능 범위 |
|------|---------------|
| 엔드포인트 URL | 자유 (RESTful 컨벤션 유지) |
| 응답 포맷 | 자유 (Pydantic response model 사용) |
| 페이지네이션 방식 | 자유 (offset/cursor) |
| 인증 방식 | 미정, 자유 선택 |
| WebSocket 메시지 포맷 | 자유 |

### 2.5 인프라

| 항목 | 변경 가능 범위 |
|------|---------------|
| 배포 방식 | Docker, 직접 실행, 클라우드 등 자유 |
| 프록시 구성 | .env로 자유 |
| 로깅 레벨/포맷 | main.py에서 자유 |
| 이미지 저장 경로 | .env로 자유 |

## 3. 조건부 변경 (CHANGE WITH CARE)

변경 가능하지만, 변경 시 영향 범위를 반드시 확인해야 하는 항목.

| 항목 | 조건 | 영향 범위 |
|------|------|-----------|
| `core/models.py` 모델 필드 추가 | 기존 필드 삭제 금지, 추가만 가능 | 모든 테스트 + 모든 모듈 |
| `core/contracts/*.py` 메서드 추가 | 기존 메서드 시그니처 변경 금지 | 모든 구현체 |
| `core/events.py` 이벤트 타입 추가 | 기존 이벤트 삭제 금지 | 모든 구독자 |
| `core/exceptions.py` 예외 추가 | 기존 예외 계층 유지 | try/except 블록 |
| DB 스키마 변경 | Alembic 마이그레이션 필수 | storage/ 전체 |
| `requirements.txt` 버전 변경 | 호환성 테스트 필수 | 전체 |
| Zustand 스토어 구조 변경 | 관련 컴포넌트 전체 검증 | 프론트엔드 전체 |

## 4. 불변/가변 판단 체크리스트

변경을 하기 전에 이 체크리스트를 확인:

```
□ 이 변경이 Section 1 (절대 불변)에 해당하나? → 해당하면 중단
□ 이 변경이 Section 3 (조건부 변경)에 해당하나? → 영향 범위 먼저 파악
□ core/ 파일을 수정하나? → 기존 인터페이스/모델 삭제/변경 금지, 추가만 가능
□ 새 모듈 간 의존이 생기나? → 반드시 core/contracts 경유
□ 데이터 흐름이 바뀌나? → ARCHITECTURE.md 업데이트 필요
□ 테스트가 깨지나? → 테스트 먼저 수정, 이유 문서화
```
