# 003. AI 자율 운영을 위한 문서 체계 구축 & 의도 중심 주석 전환 (2026-03-25)

## 배경 — 왜 이 작업을 했나

이 프로젝트는 좀 특이하다. 사람이 코딩하고 AI가 돕는 게 아니라, **AI(GitHub Copilot)가 A부터 Z까지 전부 개발**하고 사람이 방향을 잡는 구조다. 크롤러, 백엔드, 프론트엔드, 인프라까지 — AI가 코드를 쓰고, 디버깅하고, 리팩토링한다. 이게 가능하려면 AI가 프로젝트를 "이해"해야 하는데, 여기서 치명적인 문제가 하나 있다.

**컨텍스트 리셋**. AI 세션은 상태가 없다(stateless). 컨텍스트 윈도우가 차면 — 끝이다. 지금까지 뭘 했는지, 왜 그 방식을 선택했는지, 다음에 뭘 해야 하는지, 전부 증발한다. 마치 매일 아침 기억이 리셋되는 개발자와 일하는 것과 같다. 그 개발자가 아무리 뛰어나도, 어제 뭘 했는지 모르면 쓸모가 없다.

기존에도 문서는 있었다. `TECH_SPEC.md`에 기술 요구사항, `DEV_PHILOSOPHY.md`에 개발 철학, `ERROR_LOG.md`에 에러 기록, `devlog/`에 작업 일지. 나쁘지 않았다. 하지만 **AI 자율 운영에는 부족**했다. 빠진 것들이 있었다:

- 문서를 "언제, 무엇을, 어떻게" 업데이트해야 하는지의 프로토콜
- 세션 간 인수인계 방법 (다음 AI가 바로 이어서 작업할 수 있는 형식)
- 자율 판단 기준 (AI가 혼자 결정해도 되는 것 vs 사람한테 물어봐야 하는 것)
- Git 워크플로우 (AI가 브랜치를 어떻게 관리하고, 커밋은 어떤 규칙으로 하는지)
- 그리고 가장 중요한 것: **코드 주석이 "기능"이 아니라 "의도"를 말해야 한다는 것**

## 뭘 했나 — 구현 내용

### 1. 문서 체계 5종 신규 생성

기존 문서들이 "프로젝트가 뭔지"는 설명했지만, "AI가 어떻게 운영해야 하는지"는 빠져 있었다. 그래서 5개의 새 문서를 만들었다. 각각 왜 필요한지부터.

**AI_GUIDE.md — AI의 운영 매뉴얼**

단순한 코딩 컨벤션 문서가 아니다. AI가 이 프로젝트에서 일하기 위한 **전체 운영 프로토콜**이다. 코드 스타일? 당연히 포함돼 있다. 하지만 진짜 핵심은 — 문서 라이프사이클, 세션 인수인계, Git 워크플로우, 자율 판단 가이드라인. "코드를 어떻게 쓸까"가 아니라 "AI가 어떻게 이 프로젝트를 운영할까"에 대한 답이다.

**ARCHITECTURE.md — 구조의 지도**

모듈 의존성 그래프, 데이터 파이프라인 흐름, DB 스키마, API 설계를 시각적으로 정리했다. AI가 새 기능을 구현할 때 가장 먼저 해야 하는 질문이 "이 코드를 어디에 넣지?"인데, 이 문서가 그 답을 준다. `container.py` 하나로 DI를 관리하고, 모듈 간 직접 import를 금지하는 구조 — 이걸 모르면 AI가 아무 데나 코드를 넣어버린다.

**INVARIANTS.md — 절대 깨뜨리면 안 되는 것들**

이게 왜 필요하냐면, AI는 빠르게 반복(iterate)하면서 코드를 고친다. 그런데 그 과정에서 "이건 건드리면 안 되는데..." 같은 것까지 바꿔버릴 수 있다. 계약 기반 결합, DI 패턴, 코어 순수성, EventBus 통신 — 이런 불변 규칙 6가지를 명시했다. 반대로, 자유롭게 바꿔도 되는 것들도 정리했다. AI에게 "여기까지는 자유, 여기부터는 금지"라는 경계선을 그어준 셈이다. 이 경계가 있어야 AI가 자신감을 갖고 빠르게 작업할 수 있다.

**GLOSSARY.md — 도메인 용어 사전**

이 프로젝트는 식료품 가격 비교 서비스다. 도메인 용어가 중요한데, 특히 **한우 등급**(1++, 1+, 1, 2, 3등급)과 **냉동/냉장 구분**이 핵심이다. 냉동 삼겹살과 냉장 삼겹살은 2-5배 가격 차이가 난다. AI가 이 차이를 모르면? 크롤링 데이터를 파싱할 때 냉동과 냉장을 섞어버리고, 사용자에게 완전히 잘못된 가격 비교를 보여준다. KAMIS 카테고리 코드, "기준 가격", "가격 오염", "전략 캐스케이드" 같은 프로젝트 특화 용어도 정의해뒀다.

**STATUS.md — 실시간 프로젝트 현황판**

가장 자주 업데이트되는 문서. 9개 Phase의 진행률, 현재 작업 중인 항목, 블로커, 다음 우선순위를 한눈에 보여준다. 새 AI 세션이 시작되면 이 문서부터 읽으면 "아, 지금 여기까지 왔고, 다음엔 이걸 해야 하는구나"를 즉시 파악할 수 있다.

**DECISIONS.md — AI 자율 판단 추적기**

AI가 자율적으로 내린 기술적 결정을 기록하는 곳. 예를 들어 "Alembic 대신 raw SQL migration을 쓰기로 했다" 같은 결정을 — 왜 그렇게 했는지, 대안은 뭐였는지와 함께 기록한다. 상태 추적이 핵심이다: `적용됨 → 사람리뷰대기 → 승인됨/오버라이드됨`. 사람이 나중에 리뷰하고 "아니, 이건 Alembic으로 돌려"라고 오버라이드할 수도 있다. AI의 자율성을 보장하면서도, 사람이 최종 결정권을 갖는 구조.

### 2. AI_GUIDE.md 대폭 확장 — "AI의 외장 장기 기억"

AI_GUIDE.md는 원래 코딩 컨벤션 위주였는데, 4개 섹션을 대폭 추가했다. 이걸 한마디로 표현하면: **AI의 외장 하드디스크를 만들었다**.

**§6 문서 라이프사이클 프로토콜**

"새 기능을 구현하면 ARCHITECTURE.md의 모듈 다이어그램을 업데이트하라", "에러를 발견하면 ERROR_LOG.md에 기록하라", "자율 결정을 내리면 DECISIONS.md에 추가하라" — 이런 트리거 기반 업데이트 규칙을 정의했다. 문서가 업데이트 안 되면 죽은 문서다. 이 프로토콜이 문서를 살아있게(living document) 만든다.

**§7 세션 인수인계 프로토콜**

세션이 끝날 때(또는 컨텍스트가 차기 직전에) 반드시 devlog를 작성하는 규칙. 포맷은 블로그 스타일 — 뭘 했고, 뭘 시도했다 실패했고, 뭘 발견했고, 다음에 뭘 해야 하는지. 다음 AI 세션이 이 devlog 하나만 읽으면 바로 이어서 작업할 수 있는 수준으로. 이게 되면 컨텍스트 리셋의 타격이 최소화된다.

**§8 Git 워크플로우**

AI가 Git을 다루는 규칙. 브랜치 전략(`feature/*`, `fix/*`, `docs/*`), 커밋 메시지 규칙(conventional commits), PR 템플릿. 전부 AI가 사람 개입 없이 실행할 수 있게 설계했다. 핵심 원칙: **문서 커밋과 코드 커밋은 분리한다**. 문서 변경이 코드 변경과 섞이면 리뷰가 지옥이 된다.

**§9 자율 판단 기준**

AI가 혼자 결정해도 되는 것: 변수명, 내부 구현 방식, 에러 핸들링 전략, 테스트 코드 구조. 사람한테 물어봐야 하는 것: 새 외부 의존성 추가, DB 스키마 변경, API 엔드포인트 설계, 아키텍처 패턴 변경. 이 기준이 없으면 AI는 두 가지 극단 중 하나로 간다 — 너무 소극적으로 매번 물어보거나, 너무 공격적으로 아무 거나 바꿔버리거나.

### 3. 주석 철학 전환: "기능 → 의도"

이게 이번 작업에서 가장 중요한 인사이트였다.

기존 주석을 보자:

```python
# 딜레이 적용
await asyncio.sleep(random.uniform(1, 3))
```

새 AI 세션이 이 코드를 보면? "아, 1-3초 랜덤 딜레이구나." 끝이다. 그런데 **왜** 딜레이를 걸어야 하는지는 모른다. 성능 최적화를 위해 이 딜레이를 줄여도 될까? 없애도 될까?

의도 중심 주석으로 바꾸면:

```python
# 봇 탐지 회피: 인간처럼 불규칙한 간격을 둬야 차단 안 당함
# 너무 빠르면 IP 차단, 너무 느리면 크롤링 효율 저하
await asyncio.sleep(random.uniform(1, 3))
```

이제 새 AI는 안다: "이 딜레이는 봇 탐지 회피용이니까, 줄이면 차단당할 수 있고, 없앨 수는 절대 없구나." **의도를 알면 올바른 판단을 할 수 있다.**

이건 비단 AI만의 문제가 아니다. 사람 개발자도 마찬가지다. 하지만 사람은 슬랙 메시지를 뒤지거나 동료한테 물어볼 수 있다. AI는 코드와 문서밖에 없다. 코드에 의도가 없으면, AI에겐 그 의도가 세상에 존재하지 않는 것이다.

### 4. 기존 코드 주석 개선 (14개 파일)

코어 Python 파일 14개를 전수 감사(audit)해서 의도 중심 주석으로 전환하는 작업을 시작했다. 크롤러 엔진, 프록시 매니저, 스토리지 인터페이스, 설정 파일 등 — 특히 "왜 이렇게 했는지"가 빠져 있던 곳들을 집중적으로 보완했다. 이 작업은 진행 중(comment-audit)이며, 별도 커밋으로 분리할 예정이다.

## 시도했다가 실패한 것

- **처음엔 문서를 "정적 레퍼런스"로 설계했다.** ARCHITECTURE.md를 한 번 쓰고 끝, STATUS.md도 가끔 업데이트하면 되겠지 — 라고 생각했는데, 사용자가 핵심을 짚었다. "작업하면서 업데이트 안 하면 죽은 문서야." 맞는 말이었다. 그래서 "트리거 기반 업데이트" 시스템으로 재설계했다. 새 기능 추가 → ARCHITECTURE 업데이트, 에러 발견 → ERROR_LOG 기록, 세션 종료 → devlog 작성. 이런 식의 자동 업데이트 트리거.

- **첫 번째 devlog 포맷은 건조한 체크리스트였다.** "뭘 했다, 뭘 했다, 뭘 했다" — 팩트만 나열하는 형식. 사용자가 피드백을 줬다: "AI는 팩트보다 의도를 이해해야 한다. 블로그처럼 써라." 그래서 지금의 내러티브 스타일로 바꿨다. "왜 이걸 했고, 뭘 시도했다 실패했고, 뭘 배웠는지" — 이런 맥락이 있어야 다음 AI가 제대로 이어받을 수 있다.

## 발견한 것

- **"문서 = AI의 외장 메모리"** — 이번 작업의 핵심 인사이트. AI 세션은 상태가 없다. 세션이 끝나면 모든 맥락이 사라진다. 문서만이 세션을 넘어 살아남는 유일한 것이다. 그러니까 문서는 "있으면 좋은 것"이 아니라, AI 기반 개발에서 **생존에 필수적인 인프라**다.

- **문서 업데이트 우선순위가 있다.** 컨텍스트가 죽기 직전에 시간이 1분밖에 없다면? `devlog 인수인계 > STATUS.md > ERROR_LOG` 순서다. devlog 인수인계만 제대로 쓰면, 다음 세션이 나머지를 복구할 수 있다. STATUS.md가 없으면 현재 상태를 파악하는 데 시간이 걸리지만 불가능하진 않다. 하지만 devlog 인수인계가 없으면? 다음 AI는 처음부터 시작해야 한다.

- **의도 주석은 이중 목적을 가진다.** AI가 코드를 이해하는 데 도움이 되는 것은 물론이고, 인라인 문서 역할도 한다. 그리고 이 문서는 오래 살아남는다 — "HOW"는 리팩토링할 때마다 바뀌지만, "WHY"는 근본적인 요구사항이 바뀌지 않는 한 유효하다. `# 봇 탐지 회피` 주석은 우리가 크롤링을 그만두지 않는 한 계속 유효한 정보다.

- **INVARIANTS 분리가 AI에게 자신감을 준다.** "절대 바꾸면 안 되는 것"과 "자유롭게 바꿔도 되는 것"을 명확히 분리하니까, AI가 변경 가능한 영역에서는 주저 없이 빠르게 반복할 수 있다. 경계가 불분명하면 AI는 보수적으로 행동하거나 (비효율), 무시하고 돌파하거나 (위험) — 둘 다 좋지 않다.

- **용어 사전(GLOSSARY)이 생각보다 중요하다.** "냉동 삼겹살"과 "냉장 삼겹살"의 가격이 2-5배 차이 난다는 걸 AI가 모르면, 데이터 파싱에서 이 둘을 같은 카테고리로 묶어버릴 수 있다. 도메인 지식 부재로 인한 버그는 테스트로도 잡기 어렵다 — 코드는 "정상 동작"하니까. 로직이 틀린 거지 코드가 깨진 게 아니다.
