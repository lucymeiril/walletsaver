# 기획서 검수 보고서 (GPT-5.4)

## 전체 평가
기획서 자체의 밀도는 높고, 화면/API/스키마까지 한 번에 정리하려는 의도는 좋습니다. 다만 현재 코드베이스와 운영 현실을 대입하면 **“좋은 확장 설계”와 “지금 당장 안전하게 붙일 설계”가 섞여 있어 B- 수준**입니다. 특히 현행 계약 인식 오류, SQLite 한계 과소평가, 커뮤니티·배달·플러그인 요구 누락, 인증 수명주기 미정리가 커서 그대로 구현에 들어가면 기능은 늘어도 결합도와 운영 리스크가 함께 커질 가능성이 높습니다.

## 🔴 놓친 중요 사항
1. **배달음식 가격 핫딜 확인 기능이 사실상 빠져 있습니다.**  
   사용자 명시 요구였지만 본 spec은 마트/주유소/커뮤니티 중심이고, `delivery_items` 기반 사용자 기능·API·UX가 없습니다. 현재 저장소에는 `DeliveryItem` 스키마가 이미 있으나 실데이터는 0건이며, 2차 분석도 배달앱 수집 한계를 명시했습니다.  
   **제안:** 별도 장으로 분리해서 “주소 의존 가격/배달비/최소주문금액/쿠폰 반영/수집 가능 범위”를 먼저 정의해야 합니다.

2. **커뮤니티 핫딜가 제시 기능의 핵심 연결 설계가 빠졌습니다.**  
   prior analysis에서 이미 `posts.product_id`가 0건이라 적정가 제안이 사실상 미동작이라고 지적됐습니다. 현재 백엔드는 `product_ids`를 받아도 `body.product_ids[0]`만 `posts.product_id`에 저장하는 구조라 다중 상품 연결도 깨져 있습니다.  
   **제안:** “게시글-상품 연결”을 우선 복구하세요. 최소한 `post_products` 같은 매핑 테이블 여부를 결정하고, `suggested_tier` 재계산 시점/근거 데이터/KAMIS 부재 시 fallback까지 명시해야 합니다.

3. **플러그인 시스템 요구가 완전히 빠졌습니다.**  
   저장소에는 crawler 쪽 `plugin.yaml` 기반 플러그인 관리와, frontend 쪽 권한/manifest 기반 플러그인 런타임이 이미 존재합니다. 그런데 본 spec의 프로필/장바구니/상품상세/알림 설계는 어떤 플러그인 슬롯에 확장 가능한지, 어떤 권한이 필요한지, 사용자 설정과 어떻게 연결되는지 전혀 언급이 없습니다.  
   **제안:** 최소한 `profile`, `cart`, `product detail`, `dashboard-widget`에 대한 플러그인 slot/permission/read-only contract를 별도 부록으로 추가해야 합니다.

4. **인증 수명주기 변경점이 누락됐습니다.**  
   `deleted_at`, `email_verified`, OAuth 링크 해제, 비밀번호 변경, 탈퇴 유예를 추가하려면 로그인/리프레시/`require_auth` 전부가 새 상태를 검사해야 합니다. 현재 인증은 stateless JWT라 토큰 버전/세션 폐기 설계가 없고, 스펙도 이를 다루지 않습니다.  
   **제안:** `deleted_at`, `is_active`, `email_verified`, `token_version`(또는 세션 테이블) 반영 규칙을 인증 설계에 추가하세요.

5. **현행 프론트/백엔드 계약과의 연결이 부정확합니다.**  
   spec은 “현재 `GET /api/auth/profile`”라고 적지만, 실제 프론트는 `/api/auth/me`, 백엔드는 `/api/auth/me`, `/api/users/me`를 사용합니다. 장바구니도 현재 프론트는 `shoppingList` persisted store를 사용하므로 단순 API 추가가 아니라 상태 마이그레이션이 필요합니다.  
   **제안:** “현행 계약 표”를 다시 써서 실제 엔드포인트/스토어 키 기준으로 migration plan을 수정해야 합니다.

6. **장바구니/찜의 DB 제약조건 설계가 부족합니다.**  
   API 문서상으론 중복 시 수량 증가지만, `cart_items`에는 이를 보장하는 unique 제약이 없습니다. 동시 요청이나 다중 탭 상황에서 중복 row, lost update, favorite/alert 중복 생성이 발생할 수 있습니다.  
   **제안:** 최소한 `(user_id, product_id, source)` 수준의 UPSERT 전략과 optimistic locking 또는 atomic increment 정책을 정의하세요.

## 🟡 문제될 수 있는 부분
1. **[높음] API breaking change 위험**  
   현재 프론트는 `/api/auth/me`, `/api/auth/me PUT`, `/api/users/me/favorites`, `/api/users/me/alerts`를 직접 사용합니다. spec의 새 경로만 구현하면 기존 프론트/테스트가 바로 깨집니다.  
   **완화:** 기존 엔드포인트 유지 + alias 제공 + 응답 shape 호환 기간 명시가 필요합니다.

2. **[높음] 기존 데이터 마이그레이션 충돌 가능성**  
   `products` 1171건은 정규화 실패 상태이고, `posts` 217건은 테스트/운영 데이터가 혼재합니다. 이런 상태에서 `canonical_name`, `cross_mart_matches`, `email_verified=false` 같은 새 규칙을 일괄 적용하면 품질이 더 나빠질 수 있습니다.  
   **완화:** 백필을 “자동 적용”보다 “배치 산출 → 검토 → 확정” 단계로 나누고, 기존 사용자/OAuth 계정의 verified 기본값 정책을 별도 정의하세요.

3. **[높음] 보안 설계가 일부 취약합니다**  
   이메일 인증 토큰을 평문 저장하는 안은 DB 유출 시 계정 탈취로 이어집니다. 또한 현재 refresh token은 서버 저장/폐기 개념이 없어 탈퇴·비밀번호 변경·OAuth 해제 뒤에도 유효 기간 동안 살아남을 수 있습니다.  
   **완화:** 이메일 토큰은 hash 저장, refresh token은 `token_version` 또는 세션 테이블 기반 폐기 전략을 넣어야 합니다.

4. **[높음] SQLite 위에 write-behind analytics는 과설계일 수 있습니다**  
   지금 스택은 SQLite 공유 파일 + WAL + 단일 writer 특성이 핵심입니다. 여기에 이벤트 큐, 배치 writer, 집계 worker, cart write, community write가 동시에 붙으면 락 경합과 장애 은닉이 먼저 옵니다.  
   **완화:** SQLite 단계에서는 direct insert + 저빈도 집계 또는 analytics 분리 DB가 더 현실적입니다.

5. **[중간~높음] 커뮤니티 적정가 표시가 사용자에게 오해를 줄 수 있습니다**  
   현재 운영 데이터에서 `posts.product_id` 연결이 거의 없고, `attributes`도 비어 있습니다. 이런 상태에서 “적정가” 배지를 노출하면 실제론 `unknown/no_data`가 많거나, 근거가 약한 평균값이 표시될 수 있습니다.  
   **완화:** 근거 source, 샘플 수, confidence를 함께 보여주고 데이터 부족 시 적극적으로 “판단 불가”를 노출해야 합니다.

6. **[중간] 장바구니 UX만으로 ‘정보 부족’ 문제는 해결되지 않습니다**  
   spec이 장바구니 카드에 이미지/카테고리/원가/유효기간을 넣으려 하지만 현재 `products.image_url`, `attributes` 품질이 낮습니다. 즉 UX 레이어를 풍부하게 만들어도 원본 데이터가 비면 결국 빈 카드만 늘어납니다.  
   **완화:** 장바구니 개선보다 먼저 상품 메타데이터 보강과 가격 freshness 정책을 우선해야 합니다.

7. **[중간] 3-tier 가격 비교 전략은 내부적으로는 합리적이지만 사용자에겐 직관적이지 않을 수 있습니다**  
   “정부 기준가”, “카테고리 평균”, “비교 데이터 없음”이 같은 위치에서 같은 배지 톤으로 나오면 사용자는 동일 신뢰도로 받아들일 가능성이 큽니다.  
   **완화:** 최종 UI는 한 줄 결론 + 근거 뱃지(`KAMIS 기준`, `동일 카테고리 15개 평균`, `데이터 부족`) 구조로 단순화하세요.

8. **[중간] 30일 계정 삭제 유예는 스타트업 단계에 비해 운영 복잡도가 큽니다**  
   복구 UX, scheduled purge, 토큰 폐기, 개인정보 보존 정책, 이벤트 로그 삭제를 모두 정합적으로 맞춰야 합니다. 현재 구현 기반을 보면 즉시 처리 또는 짧은 복구 기간이 더 현실적입니다.  
   **완화:** 초기엔 즉시 비활성화 + 7일 복구 정도로 축소하는 편이 낫습니다.

9. **[중간] 외부 의존성 가용성 차이가 큽니다**  
   Opinet/KAMIS는 상대적으로 현실적이지만, 배달앱 가격·배달비·주소별 메뉴는 정책상 안정 수집이 어렵습니다. 이메일 발송, 이미지 저장소, Redis, PostgreSQL 레플리카도 현재 repo 기준 즉시 사용 가능한 상태가 아닙니다.  
   **완화:** 외부 의존 기능은 “가용 API 존재”와 “현재 프로젝트에 운영 배선 존재”를 구분해 우선순위를 정해야 합니다.

## 🔵 개선 제안
1. **P0 범위를 줄이세요.**  
   1차 릴리스는 `현행 계약 안정화 → community product 연결 복구 → 상품 정규화/카테고리 품질 개선 → 최소 프로필/장바구니 서버화`까지만 잡는 것이 안전합니다.

2. **회원 기능은 `/api/auth/*`와 `/api/users/*`를 재설계하기보다 호환 래퍼부터 두세요.**  
   현재 프론트가 이미 쓰는 `/api/auth/me`와 `/api/users/me`를 유지한 채 내부 구현만 확장하는 편이 리스크가 훨씬 작습니다.

3. **커뮤니티 적정가 제안은 별도 Epic으로 분리하세요.**  
   지금은 “UI 표시”보다 “게시글-상품 연결 정합성”이 먼저입니다. `post_products` 여부, 단일/복수 상품 정책, 재계산 트리거를 먼저 고정해야 합니다.

4. **장바구니는 DB 스키마보다 원자성부터 정의하세요.**  
   `add`, `merge`, `quantity update`를 모두 UPSERT 또는 atomic increment 관점으로 다시 써야 합니다. API 문서만으로는 구현자마다 동작이 달라질 가능성이 큽니다.

5. **가격 비교 배지에는 신뢰도 표기를 넣으세요.**  
   예: `적정가 (KAMIS 기준)`, `비교 참고 (동일 카테고리 15개 평균)`, `판단 불가`. 이게 사용자 오해를 줄입니다.

6. **플러그인 시스템을 spec에 편입하세요.**  
   최소한 plugin slot, 권한(`read:products`, `write:preferences` 등), sandbox 제한, 사용자 설정 저장 위치를 명시해야 향후 커스텀 기능과 충돌하지 않습니다.

7. **analytics는 현 단계에서 ‘추천 준비용 최소 수집’으로 축소하세요.**  
   검색/상품조회/찜추가 정도만 직접 저장하고, write-behind·15분 집계·파일 dump 재시도는 PostgreSQL/Redis 도입 후로 미루는 편이 현실적입니다.

## 📋 구현 우선순위 제안
1. **현행 API 계약 정리 및 호환 유지**  
   실제 사용 중인 `/api/auth/me`, `/api/users/me`, persisted `shoppingList`를 기준으로 migration baseline부터 바로잡아야 전체 구현 리스크가 줄어듭니다.

2. **커뮤니티 상품 연결 복구 + 적정가 제안 최소 정상화**  
   `posts.product_id=0건` 상태를 먼저 해결해야 “커뮤니티 핫딜가 제시”가 살아납니다. 사용자 요구와 가장 직접 연결됩니다.

3. **상품 정규화/카테고리 개선**  
   현재 1171개 중 24개만 category가 있어 마트 상세 모달, 3-tier 비교, 추천, 장바구니 정보 강화가 모두 상류 데이터에 막혀 있습니다.

4. **프로필 기능 중 저위험 항목부터**  
   닉네임/기본 프로필 조회, 비밀번호 변경, OAuth 링크 상태 조회 정도부터 구현하고, 이메일 변경·이미지 업로드·탈퇴 유예는 뒤로 미루는 편이 안전합니다.

5. **장바구니 서버 영속화**  
   단, product metadata와 atomic upsert 정책이 준비된 뒤에 진행해야 UX가 실제로 좋아집니다.

6. **마트 상세 모달 고도화**  
   `detail-modal`은 최소 정보부터 시작하고, related hotdeals/price_history/cross-mart는 데이터 품질이 확보되는 범위에서 순차 확장하세요.

7. **주유소(Opinet) 연동**  
   외부 API 실현 가능성이 높아 빠른 성과가 가능하지만, 현재 핵심 가치(가격 비교/커뮤니티 검증)보단 후순위가 맞습니다.

8. **analytics / Redis / PostgreSQL 전환 / read replica 논의**  
   현재 규모와 SQLite 현실을 고려하면 가장 마지막 단계가 적절합니다.

9. **배달음식 가격 핫딜 확인 + 플러그인 확장**  
   둘 다 중요하지만 외부 제약과 확장 설계가 커서, 코어 데이터 정합성이 확보된 뒤 별도 트랙으로 가는 편이 낫습니다.

## ⚠️ SQLite 한계 관련 주의사항
- **WAL을 써도 writer는 1개입니다.** 장바구니, 커뮤니티, 이벤트 수집, 크롤 데이터 반영이 겹치면 lock contention이 생깁니다.
- **실제 connection pooling 이점이 거의 없습니다.** 현재도 SQLite는 `NullPool/StaticPool` 성격이 강하며, spec의 “동시 연결 30” 목표는 throughput 보장이 아닙니다.
- **read replica 설계는 SQLite 단계에선 사실상 무의미합니다.** 이건 PostgreSQL 전환 후 논의할 주제입니다.
- **write-behind + 인메모리 큐 + 파일 dump 재시도는 장애를 숨길 수 있습니다.** SQLite 단계에서는 단순하고 관측 가능한 쓰기 모델이 더 안전합니다.
- **중복 방지는 앱 로직만으로 부족합니다.** cart/favorite/alert는 SQLite에서도 unique constraint + UPSERT를 써야 동시성 버그를 줄일 수 있습니다.
- **캐시 전략도 과하면 안 됩니다.** 프로세스 로컬 TTLCache는 다중 프로세스에서 일관성이 없으므로, SQLite 단계에서는 캐시보다 정확한 invalidation 범위 축소가 더 중요합니다.
