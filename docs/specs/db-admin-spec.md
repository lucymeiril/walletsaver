## 1. 프로젝트 개요

### 서비스 구조

```
[크롤러 17개+] → [크롤러 관리자 1차 승인] → [DB 관리자 최종 승인] → [DB 반영] → [웹사이트가 DB 읽기] → [사용자에게 표시]
```

### DB 관리자의 핵심 역할

| 역할 | 설명 |
|------|------|
| **데이터 문지기** | 크롤러가 수집한 데이터를 검토하고 품질이 보장된 것만 DB에 반영 |
| **상품 큐레이터** | 상품 정보, 카테고리, 키워드를 정리하여 사용자 검색 경험을 최적화 |
| **가격 감시자** | 기준가 대비 핫딜가를 모니터링하고, 이상치를 걸러내어 신뢰도 유지 |
| **품질 관리자** | 데이터 중복, 누락, 이상치를 탐지하고 정리하여 서비스 품질 보장 |

### 관리 대상 데이터

| 데이터 | 출처 | 예상 규모 |
|--------|------|----------|
| 상품 (products) | 정부(KAMIS/KOSIS), 마트(이마트/홈플러스/롯데/코스트코), 커뮤니티 | 수천 건 |
| 기준가 (baseline_prices) | 정부 공인가, 도매가 | 수만 건 |
| 할인가 (discount_history) | 마트 실제 판매가 | 수만~수십만 건 |
| 핫딜가 (hotdeal_prices) | 커뮤니티 게시글 (참고용, 평균 계산 제외) | 수천 건 |
| 수집 대기열 (pending_ingestions) | 크롤러 제출 → 2단계 승인 | 수십~수백 건 |

## 2. 현행 시스템 분석

### 2.1 현재 구현 상태

| 영역 | 상태 | 세부 |
|------|------|------|
| 기본 CRUD | ✅ 완성 | 상품/카테고리/키워드 모두 동작 |
| 필터링/정렬/페이지네이션 | ✅ 완성 | Products에서 구현 |
| 2단계 승인 워크플로 | ✅ 완성 | 크롤러 관리자 → DB 관리자 승인 체인 |
| 가격 티어 관리 | ⚠️ 부분 | 티어 설정은 파일 기반 (tier_config.json) |
| 품질 리포트 | ⚠️ Mock 의심 | completeness/accuracy가 고정값일 가능성 |
| 에러 처리 | ❌ 미흡 | try-finally만, except 없음 |
| 코드 구조 | ⚠️ 개선 필요 | Products.jsx 617줄 단일 파일 |

### 2.2 현재 발견된 주요 문제점

1. **Products.jsx 617줄** — 유지보수 불가, 컴포넌트 분리 필요
2. **에러 처리 부재** — API 에러 시 사용자에게 피드백 없음, console.error만
3. **Mock 데이터 혼재** — 품질 점수, 출처 상태 등이 실제 계산인지 고정값인지 불명확
4. **응답 포맷 불일치** — items vs data vs 직접 배열, camelCase vs snake_case 혼용
5. **로딩/에러 UX 미흡** — 스켈레톤, 토스트 없이 텍스트만 표시
6. **CSV export 불완전** — BOM, 인코딩 미처리 (한글 깨짐 가능)
7. **N+1 쿼리 문제** — 상품 정렬 시 서브쿼리 3개 사용

### 3.1 대시보드

#### 💬 기획 토론

```
[기획자A - UX]: 관리자가 출근해서 처음 보는 화면이니까, "오늘 뭘 해야 하는지"가 
3초 안에 파악돼야 합니다. 현재는 StatCard 4개 + 게이지 + 최근 수집 표인데, 
"행동을 유도하는 정보"가 부족해요. 숫자만 보여주고 끝입니다.

[기획자B - 데이터]: 동의합니다. 관리자 입장에서 가장 먼저 확인하는 건 
"대기 중인 수집 데이터가 몇 건인지", "이상치가 발생한 상품이 있는지"입니다. 
현재 pending count는 표시하지만, 긴급도(얼마나 오래 대기했는지)가 없어요.

[기획자C - 비즈니스]: 서비스 운영 관점에서 "데이터가 신선한가"가 핵심이에요. 
이마트 데이터가 3일 전 것이면 사용자가 보는 가격이 틀릴 수 있거든요. 
각 출처별 "마지막 수집 시각"을 한눈에 봐야 합니다.

[기획자A]: freshness 로직이 현재 1시간/6시간만 구분하는데, 출처별로 다른 
기준이 필요하지 않을까요? 정부 데이터는 주 1회 업데이트지만 마트는 매일이니까.

[기획자B]: 맞아요. 그리고 품질 점수 게이지가 Mock인 것 같다는 문제가 있는데, 
실제 데이터 기반으로 "이번 주 품질 트렌드"를 보여줘야 합니다.

→ 합의: 대시보드는 "액션 유도형"으로 재설계. 4가지 핵심 영역으로 구성:
   ① 긴급 알림 (대기 데이터, 이상치, 오래된 데이터)
   ② 데이터 현황 (총 상품수, 가격 이력수 등 — 기존 StatCard 유지)
   ③ 출처별 신선도 (각 크롤러별 마지막 수집 시각 + 상태)
   ④ 최근 활동 로그 (기존 유지하되 클릭 시 해당 페이지로 이동)
```

#### 핵심 작업

| 작업 | 설명 |
|------|------|
| 긴급 사항 확인 | 대기 중인 수집 데이터 건수, 이상치 발생 건수, 경고 상태인 출처 |
| 데이터 현황 파악 | 총 상품수, 가격 이력수, 카테고리수, 키워드수 |
| 출처별 상태 확인 | 각 크롤러(이마트/홈플러스/KAMIS 등)의 마지막 수집 시각 + 건강 상태 |
| 빠른 이동 | 긴급 알림 클릭 → 해당 탭으로 바로 이동 |

#### 현재 문제점

- 게이지 점수가 Mock 데이터일 가능성 높음
- freshness 로직이 단순 (1시간/6시간만 구분)
- 행동 유도 없이 숫자만 나열

#### 개선 방안

| 개선 | 설명 | 우선순위 |
|------|------|---------|
| **긴급 알림 배너** | 대기 N건, 이상치 N건, stale 출처 N개 — 클릭하면 해당 탭 이동 | P0 |
| **출처별 신선도 패널** | 크롤러별 마지막 수집 시각 + 색상 (초록/노랑/빨강) | P0 |
| **품질 점수 실제 연동** | Mock 제거, 실제 이상치/중복/누락 기반 점수 계산 | P1 |
| **출처별 주기 기준** | 정부(주 1회), 마트(매일), 커뮤니티(실시간) 별 다른 stale 기준 | P1 |
| **주간 트렌드 미니차트** | 지난 7일 수집 건수 + 승인률 추이 (스파크라인) | P2 |

#### 필수 기능 목록

1. **[P0]** 긴급 액션 알림 (pending ingestions, outliers, stale sources)
2. **[P0]** 데이터 현황 요약 카드 4개 (기존 유지)
3. **[P0]** 출처별 마지막 수집 시각 + 건강 상태
4. **[P1]** 품질 점수 실제 계산 + 게이지 표시
5. **[P1]** 최근 수집 활동 테이블 (클릭 시 Inbox로 이동)
6. **[P2]** 주간 수집/승인 트렌드 미니차트

### 3.2 수집 관리 (Inbox)

#### 💬 기획 토론

```
[기획자B - 데이터]: 이게 DB 관리자의 핵심 업무입니다. 크롤러 관리자가 1차 승인한 
데이터가 여기로 들어오면, DB 관리자가 최종 검토 후 승인/거부합니다. 
현재 문제는 "이마트 크롤링 데이터 277건이 들어왔을 때" 하나하나 확인할 수 없다는 거예요.

[기획자A - UX]: 현재 카드 목록 → 상세 모달 구조인데, 상세 모달에서 
데이터 테이블이 처음 7개 컬럼만 표시(slice(0,7))되고, 편차 표시 기준이 
hardcoded(50%/25%)입니다. 관리자가 "이 데이터가 왜 이상한지" 직관적으로 
파악하기 어려워요.

[기획자C - 비즈니스]: 실무적으로 보면, 대부분의 크롤링 데이터는 문제가 없어요. 
문제가 있는 소수의 항목만 빠르게 걸러내고, 나머지는 일괄 승인하는 게 효율적입니다.
"품질 점수 95점 이상이면 자동 승인" 같은 규칙도 필요하지 않을까요?

[기획자B]: 자동 승인은 위험할 수 있어요. 대신 "문제 항목만 하이라이트"해서 
관리자가 그것만 확인하고, 나머지는 한 번에 승인하는 방식이 좋겠습니다.

[기획자A]: 동의합니다. 그리고 부분 승인 기능이 있는데, 현재 체크박스로만 
선택하게 돼 있어요. "이상치만 선택 해제" 같은 빠른 필터가 필요합니다.

→ 합의: 
   ① 목록에서 품질 점수 + 문제 항목 수를 바로 표시
   ② 상세 화면에서 "문제 항목만 보기" 필터 제공
   ③ "정상 항목 전체 선택" → 일괄 승인 워크플로
   ④ 거부 시 사유 선택(드롭다운) + 자유 입력 병행
```

#### 핵심 작업

| 작업 | 설명 |
|------|------|
| 대기 데이터 확인 | 어떤 크롤러에서 몇 건이 들어왔는지, 품질 점수는 얼마인지 |
| 데이터 검토 | 항목별 가격, 이름, 카테고리 등 확인 + 이상치/의심 항목 식별 |
| 승인/거부 결정 | 전체 승인, 부분 승인(정상 항목만), 전체 거부 |
| 거부 사유 기록 | 왜 거부했는지 기록 (크롤러 관리자에게 피드백) |

#### 현재 문제점

- 데이터 항목 테이블이 처음 7개 컬럼만 표시 (`slice(0,7)`)
- 편차 임계값이 hardcoded (50%/25%)
- 부분 승인 후 UI 업데이트 지연
- 상세 데이터 fetch가 `fetch()` 직접 사용, 에러 처리 미흡

#### 개선 방안

| 개선 | 설명 | 우선순위 |
|------|------|---------|
| **문제 항목 하이라이트** | 이상치/의심 항목을 빨강/주황으로 강조, 정상 항목과 분리 | P0 |
| **빠른 필터** | "이상치만 보기", "정상만 보기", "누락 필드 있는 항목만" | P0 |
| **일괄 승인 워크플로** | "정상 항목 전체 선택" 버튼 → 이상치만 제외하고 승인 | P0 |
| **모든 컬럼 표시** | slice(0,7) 제거, 전체 필드 표시 + 가로 스크롤 or 컬럼 선택 | P1 |
| **거부 사유 템플릿** | 자주 쓰는 사유 드롭다운 (가격 이상, 중복, 필드 누락 등) | P1 |
| **배치 비교 뷰** | 이전 수집 데이터와 현재 데이터 비교 (가격 변동 확인) | P2 |
| **자동 분류 제안** | 품질 점수 기반으로 "승인 추천" / "검토 필요" 라벨 자동 부여 | P2 |

#### 필수 기능 목록

1. **[P0]** 대기/승인/거부 상태별 필터링
2. **[P0]** 크롤러별 분류 + 품질 점수 표시
3. **[P0]** 문제 항목 하이라이트 + 빠른 필터
4. **[P0]** 전체 승인 / 부분 승인 / 전체 거부
5. **[P1]** 거부 사유 템플릿 + 자유 입력
6. **[P1]** 모든 데이터 컬럼 표시 (가로 스크롤)
7. **[P1]** 승인/거부 후 즉시 UI 반영
8. **[P2]** 이전 배치 대비 가격 변동 비교

#### 관리자 시나리오: "이마트 크롤링 데이터 277건 처리"

```
1. 대시보드에서 "대기 중 3건" 알림 확인 → 클릭하여 Inbox 이동
2. Inbox 목록에서 "이마트 | 277건 | 품질 92점" 카드 확인
3. 카드 클릭 → 상세 화면 진입
4. 기본 뷰: "문제 항목만 보기" 필터 ON → 이상치 12건만 표시
5. 이상치 12건 검토:
   - 삼겹살 100g에 500원 → 가격 오류 확실 → 체크 해제
   - 양파 1kg에 15,000원 → 기존 평균 3,000원 대비 5배 → 체크 해제
   - 나머지 10건은 편차 30% 이내 → 허용 가능 → 유지
6. "정상 항목 전체 선택" → 265건 + 허용 이상치 10건 = 275건 선택
7. "부분 승인" 클릭 → 275건 DB 반영, 2건 제외
8. DB 검토자 메모: "삼겹살/양파 가격 오류 2건 제외"
9. 완료 → 다음 배치(홈플러스) 검토
```

### 3.3 상품 관리

#### 💬 기획 토론

```
[기획자A - UX]: Products.jsx가 617줄인데 이건 기획 문제가 아니라 구현 문제이긴 해요.
하지만 기획 관점에서 보면, 하나의 페이지에 너무 많은 기능이 몰려 있어요. 
소스 필터 + 검색 + 정렬 + 벌크 작업 + 행 확장 + 모달 6개...
```

| 기준가 관리 | 정부 공인 기준가 확인 및 보완 |
| 가격 통계 확인 | 평균/중앙값/표준편차 등 통계 |

#### 현재 문제점

- 티어 설정이 파일 기반 (tier_config.json), DB 아님
- 이상치 탐지 기준(IQR)이 단순, 계절성 미반영
- 가격 필터에 source 대신 priceSearch 파라미터 사용 (버그 의심)
- 통계 계산 로직: "API 우선, 없으면 프론트 계산" → 불일치 가능

#### 개선 방안

| 개선 | 설명 | 우선순위 |
|------|------|---------|
| **티어 변경 미리보기** | 임계값 수정 시 "N개 상품 등급 변경" 미리 표시 | P0 |
| **이상치 화이트리스트** | 관리자가 "정상 가격"으로 표시하여 재탐지 제외 | P1 |
| **출처별 가격 분리 뷰** | 기준가(baseline) / 할인가(discount) / 핫딜가(hotdeal) 탭 분리 | P1 |
| **기준가 수동 입력** | 정부 데이터 미수집 상품에 대해 관리자가 직접 기준가 입력 | P1 |
| **가격 필터 버그 수정** | source 파라미터 정상화 | P1 |
| **계절성 보정** | 명절/계절에 따른 이상치 기준 자동 조정 | P2 |

#### 필수 기능 목록

1. **[P0]** 티어 기준값 CRUD + 저장 — 기존 유지
2. **[P0]** 티어 변경 시 영향 미리보기
3. **[P0]** 이상치 탐지 목록 + 상세 정보 — 기존 유지
4. **[P1]** 이상치 화이트리스트
5. **[P1]** 출처별 가격 분리 뷰

7. **[P1]** 가격 이력 페이지네이션 — 기존 유지
8. **[P2]** 가격 통계 요약 — 기존 유지, 서버 계산으로 통일

### 3.7 분석/통계

#### 💬 기획 토론

```
[기획자C - 비즈니스]: 분석 탭은 "현재 서비스 상태가 건강한가?"를 
판단하는 페이지에요. 주간/월간 리포트를 만들 때 여기서 데이터를 뽑아야 하는데, 
현재 CSV export가 단순 join만 해서 BOM/인코딩 처리가 안 되어 있어요.

[기획자B - 데이터]: 품질 리포트가 Mock인 것 같다는 audit 결과가 가장 심각해요.
이상치 수, 중복 수, 누락 필드 수가 실제로 계산되지 않으면 
이 페이지의 신뢰도가 0이에요.

[기획자A - UX]: 카테고리별 평균 가격 BarChart, 가격 추이 LineChart가 있는데, 
기간 선택이 30/60/90일로 한정되어 있어요. 
"최근 1주일"이나 "커스텀 기간"도 필요하지 않을까요?

[기획자C]: 출처별 통계 테이블에서 "상태" 판단 기준이 불명확하다는 
audit 결과가 있었는데, 이건 구체적인 기준을 정해야 해요:
- Active: 24시간 이내 수집 성공
- Warning: 24~72시간 미수집
- Error: 72시간 이상 미수집 또는 마지막 수집 실패

[기획자B]: 데이터 정합성 체크도 필요해요. 예를 들어 
"카테고리가 없는 상품", "가격 이력이 없는 상품", 
"키워드가 연결되지 않은 카테고리" 같은 orphan 데이터를 찾아야 합니다.

→ 합의:
   ① 품질 리포트 실제 구현 (Mock 제거)
   ② 출처별 상태 기준 명확화 (24h/72h)
   ③ 데이터 정합성 체크 (orphan 데이터 탐지)
   ④ 기간 선택 확장 (1주/1개월/3개월/커스텀)
   ⑤ CSV export 개선 (BOM + UTF-8)
```

#### 핵심 작업

| 작업 | 설명 |
|------|------|
| 가격 추이 분석 | 상품별 가격 변동 추이 차트 확인 |
| 카테고리별 통계 | 카테고리별 평균 가격, 상품 수 등 |
| 품질 리포트 확인 | 이상치, 중복, 누락 필드 등 데이터 품질 지표 |
| 출처별 상태 확인 | 각 크롤러 출처의 수집 상태 및 레코드 수 |
| 데이터 내보내기 | CSV/JSON 형식으로 데이터 export |
| 정합성 체크 | orphan 데이터 (카테고리 없는 상품 등) 탐지 |

#### 현재 문제점

- 품질 리포트(completeness/accuracy)가 Mock일 가능성 높음
- 출처별 상태 판단 기준 불명확
- CSV export에서 BOM, 인코딩 미처리 (한글 깨짐)
- 기간 선택이 30/60/90일로 제한

#### 개선 방안

| 개선 | 설명 | 우선순위 |
|------|------|---------|
| **품질 리포트 실제 구현** | Mock 제거, DB 쿼리 기반 실제 수치 계산 | P0 |
| **출처 상태 기준 정의** | Active(24h), Warning(24-72h), Error(72h+/실패) | P0 |
| **정합성 체크** | 카테고리 없는 상품, 가격 없는 상품, 연결 없는 키워드 탐지 | P1 |
| **CSV export 개선** | BOM + UTF-8 인코딩, 날짜 형식 통일, Excel 호환 | P1 |
| **기간 선택 확장** | 1주/1개월/3개월/6개월/1년/커스텀 | P1 |
| **자동 정리 기능** | cleanup API (180일+ 오래된 데이터) UI 연결 | P2 |
| **리포트 스케줄링** | 주간/월간 자동 리포트 생성 + 다운로드 | P2 |

#### 필수 기능 목록

## 4. 전체 작업 시나리오

### 시나리오 1: 일일 루틴 (매일 아침)

```
1. [대시보드] 로그인 → 긴급 알림 확인
   - "대기 중인 수집 데이터: 5건"
   - "이상치 감지: 3건"
   - "stale 출처: KAMIS (3일 전)"

2. [수집 관리] 대기 데이터 5건 처리
   - 이마트 (277건, 품질 92점) → 이상치 12건 확인 → 부분 승인 (265건)
   - 홈플러스 (189건, 품질 96점) → 문제 없음 → 전체 승인
   - 롯데마트 (143건, 품질 88점) → 누락 필드 20건 → 부분 승인 (123건)
   - KAMIS (45건, 품질 99점) → 정부 데이터 → 전체 승인
   - 커뮤니티 핫딜 (67건, 품질 75점) → 이상치 많음 → 상세 검토

3. [상품 관리] 유사 상품 알림 확인
   - "국내산 삼겹살 100g" (이마트) ↔ "삼겹살(국산) 100g" (홈플러스) 
   → 같은 상품으로 병합

4. [분석/통계] 일일 품질 확인
   - 품질 점수 92.5점 → 정상 범위
   - 데이터 완전성 98.1% → 양호
```

### 시나리오 2: 신규 카테고리 추가

```
1. [카테고리 관리] "수산물" 하위에 "전복" 카테고리 추가
   - 부모: "수산물" → 자식: "전복" 추가
   - 속성: origin(원산지), grade(등급) 설정

2. [키워드 관리] "전복" 관련 키워드 등록
   - 키워드: "전복" 
   - 동의어: "활전복", "냉동전복", "완도전복"
   - 카테고리 연결: "수산물.전복"

3. [상품 관리] 기존 "전복" 상품들 카테고리 재분류
   - 검색: "전복" → 해당 상품 10건 선택
   - 벌크 작업: 카테고리 → "수산물.전복"으로 일괄 변경
```

### 시나리오 3: 가격 이상치 대응

```
1. [대시보드] "이상치 감지: 3건" 알림
   
2. [가격 관리] 이상치 탭 확인
   - 삼겹살 100g: 감지가격 500원 (평균 12,000원, 편차 -95.8%)
     → 크롤링 오류로 판단 → 해당 가격 기록 삭제
   - 양파 1kg: 감지가격 15,000원 (평균 3,000원, 편차 +400%)
     → 설 명절 시즌 가격 → 화이트리스트에 추가 (정상)
   - 계란 30구: 감지가격 0원 (평균 8,000원)
     → 크롤링 오류 → 해당 가격 기록 삭제

3. [분석/통계] 품질 리포트 재확인
   - 이상치 수: 3건 → 1건 (화이트리스트 제외)
   - 정확도: 99.2% → 99.5%
```

### 시나리오 4: 주간 리포트

```
1. [분석/통계] 주간 데이터 확인
   - 기간: 최근 7일
   - 수집 건수: 총 4,523건
   - 승인률: 91.2%
   - 이상치 발생: 47건 (전주 대비 -12%)
   - 새 상품 등록: 23건

2. [분석/통계] CSV export
   - 카테고리별 평균 가격 다운로드
   - 품질 리포트 다운로드
   - 출처별 수집 현황 다운로드
```

## 5. 공통 UX 개선사항

### 5.1 에러 처리 및 피드백

| 현재 | 개선 |
|------|------|
| API 에러 시 console.error만 | 토스트 알림으로 사용자에게 표시 |

### 5.2 일관된 디자인 패턴

| 항목 | 통일 기준 |
|------|----------|
| API 응답 포맷 | 항상 `{ data: ..., total: ..., error?: ... }` |
| 필드 네이밍 | snake_case 통일 (API) / camelCase 통일 (프론트) |
| 페이지네이션 | 모든 목록 20건씩, 버튼 페이지네이션 |
| 모달 디자인 | 제목 + 본문 + 하단 버튼 (취소/확인) 통일 |
| 테이블 디자인 | 체크박스 + 컬럼 헤더 정렬 + 행 hover 통일 |

### 5.3 접근성/편의성

- **키보드 단축키**: Ctrl+S (저장), Esc (모달 닫기), Enter (검색 실행)

- **다크모드**: 야간 작업 시 눈 피로 감소 (P2)

## 부록: 품질 점수 계산

```
품질 점수 = 1.0 - (missing_ratio × 0.4) - (outlier_ratio × 0.3) - (dup_ratio × 0.3)

missing_ratio: 필수 필드(name, price, source) 누락 비율
outlier_ratio: 가격이 평균 ±5배 이상 벗어난 항목 비율
dup_ratio:     동일 상품+날짜+출처 중복 항목 비율

예시:
  277건 중 누락 5건(1.8%), 이상치 12건(4.3%), 중복 3건(1.1%)
  = 1.0 - (0.018 × 0.4) - (0.043 × 0.3) - (0.011 × 0.3)
  = 1.0 - 0.0072 - 0.0129 - 0.0033
  = 0.9766 → 97.66점
```
