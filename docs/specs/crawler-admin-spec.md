# 지갑 지키미 — 크롤러 관리자 기획서

## 기획팀 토론 결과

### 기획자 구성
- **기획자A (UX 전문가)**: 모니터링 직관성, 장애 시 빠른 대응 UI
- **기획자B (크롤링 운영자)**: 실제 크롤러 운영 업무, 장애 대응, 데이터 품질
- **기획자C (비즈니스)**: 핫딜 서비스에서 크롤러 데이터의 역할, 안정성

---

## 1. 대시보드

### 운영자 목표
"전체 크롤러 상태를 한눈에 파악하고, 문제가 있으면 즉시 인지"

### 현재 문제점
- 수동 새로고침 버튼 없음 (마운트 시 1회만 호출)
- 차트가 최근 7일 고정, 날짜 범위 선택 불가
- 크롤러별 성능 분석 없음
- WebSocket/폴링 없어 실시간 아님

### 개선 방안

[기획자A]: 대시보드는 "신호등" 역할을 해야 한다. 전체 녹색이면 안심, 하나라도 빨간색이면 즉시 눈에 띄어야 한다.
[기획자B]: 크롤러별 성공률 히트맵이 있으면 좋겠다. 어떤 크롤러가 최근 자주 실패하는지 한눈에.
[기획자C]: 데이터 신선도가 중요. "이마트 데이터가 3일 전 것"이면 서비스 품질이 떨어진다.
→ 합의: 상단에 전체 상태 신호등 + 긴급 알림 배너, 중단에 크롤러별 상태 히트맵, 하단에 데이터 신선도 패널

### 필수 기능
- P0: 수동 새로고침 버튼
- P0: 실패/에러 크롤러 긴급 알림 배너 (빨간색, 상단 고정)
- P0: 크롤러별 상태 카드 (성공/실패/비활성 색상 코딩)
- P1: 데이터 신선도 패널 (각 데이터 소스 마지막 업데이트 시간)
- P1: 날짜 범위 선택 가능한 차트
- P2: 자동 새로고침 (30초 폴링 또는 WebSocket)

### 운영자 시나리오
> 아침 출근 → 대시보드 확인 → "이마트 실패 1회" 빨간 알림 → 클릭 → 로그 확인 → 재실행

## 2. 크롤러 관리

### 운영자 목표
"19개 크롤러를 개별적으로 제어하고, 실행 결과를 즉시 확인"

### 현재 문제점
- 폴링 타임아웃이 무음 (실행 중인지 타임아웃인지 구분 불가)
- "크롤러 추가" 버튼이 안내 모달만 표시 (실제 생성 불가)
- 벌크 작업 없음 (여러 개 동시 실행/비활성화)
- 설정 폼 유효성 검증 없음
- 실행 중인 크롤러 시각적 구분 부족

### 개선 방안

[기획자A]: 각 크롤러 카드에 "마지막 실행" + "수집 건수" + "성공률" 3개 핵심 지표만 보여주자.
[기획자B]: 실행 중에는 프로그레스 바 + 실시간 로그 스트리밍이 있어야 한다. 타임아웃이면 "타임아웃됨" 명확히 표시.
[기획자C]: 카테고리별 그룹핑 (마트/핫딜/쇼핑/공공)으로 관리 편의성 높이자.
→ 합의: 카테고리 그룹핑 + 실행 상태 프로그레스 바 + 타임아웃 명확 표시 + 벌크 선택

### 필수 기능
- P0: 실행 중 프로그레스/스피너 + 타임아웃 명확 표시
- P0: 실행 결과 즉시 표시 (수집 N건, 소요시간, 성공/실패)
- P0: 카테고리별 그룹핑 뷰
- P1: 벌크 선택 (전체 마트 크롤러 실행 등)
- P1: 설정 폼 유효성 검증 (URL 형식, 숫자 범위)
- P1: 실행 이력 미니 타임라인 (최근 5회)
- P2: 크롤러 추가 위저드 (plugin.yaml 템플릿 기반)

### 운영자 시나리오
> "마트 전단지 업데이트해야지" → 마트 카테고리 선택 → 이마트/홈플/롯데 3개 선택 → "선택 실행" → 프로그레스 바 → 결과 확인 (이마트 277건, 홈플 398건, 롯데 49건)

## 3. 플러그인 관리

### 운영자 목표
"어떤 크롤러가 설치되어 있고, 각각 어떤 설정인지 확인/수정"

### 현재 문제점
- YAML 뷰어에 구문 강조 없음
- 인라인 편집 불가
- 검색/필터 없음
- 난이도 별표(⭐⭐)에 설명 없음
- 실행 중인 플러그인 구분 없음

### 개선 방안

[기획자A]: YAML 보다는 폼 기반 편집이 직관적이다. YAML은 "고급" 탭으로 빼자.
[기획자B]: plugin.yaml 직접 편집은 위험하다. 필드별 폼 + 유효성 검증이 안전하다.
[기획자C]: 카테고리별로 묶고, "비활성" 플러그인은 회색 처리해서 눈에 덜 띄게.
→ 합의: 폼 기반 설정 편집 (기본) + YAML 뷰어 (고급), 카테고리 필터, 비활성 플러그인 시각 구분

### 필수 기능
- P0: 카테고리 필터 (마트/핫딜/쇼핑/공공/위치)
- P0: 활성/비활성 시각 구분 (비활성은 회색)
- P1: 폼 기반 설정 편집 (URL, 지연시간, 최대 수집 수)
- P1: 검색 (플러그인 이름/설명)
- P2: YAML 구문 강조 뷰어
- P2: 새 플러그인 템플릿 생성

## 4. 스케줄 관리

### 운영자 목표
"자동 크롤링 주기를 설정하고, 예정된 실행을 한눈에 확인"

### 현재 문제점
- "실행" 버튼이 작동하지 않음
- 커스텀 cron 식에 대한 미리보기 없음
- 비활성 스케줄 시각 구분 부족
- 다음 실행 시간 실시간 갱신 안 됨

### 개선 방안

[기획자A]: 캘린더 뷰로 이번 주 크롤링 일정을 보여주면 직관적이다.
[기획자B]: cron 대신 "매일 7시", "6시간마다" 같은 한국어 프리셋이 더 편하다. 고급은 cron 직접 입력.
[기획자C]: 스케줄 충돌 감지가 필요. 같은 시간에 5개 크롤러가 동시에 돌면 서버 부하 걸린다.
→ 합의: 한국어 프리셋 기본 + cron 고급 입력, 실행 버튼 작동, 타임라인 뷰

### 필수 기능
- P0: "즉시 실행" 버튼 작동
- P0: 한국어 프리셋 확장 (매일 7시, 매일 19시, 12시간마다 등)
- P0: cron 미리보기 (다음 3회 실행 시간 표시)
- P1: 타임라인/캘린더 뷰 (이번 주 일정)
- P1: 스케줄 충돌 경고
- P2: 스케줄 일시정지/재개

## 5. 로그 뷰어

### 운영자 목표
"크롤링 실행 이력을 검색하고, 에러를 추적하고, 보고서를 내보내기"

### 현재 문제점
- 날짜 검색 없음 (크롤러 이름만 필터)
- CSV 내보내기 필드 불완전
- "부분 성공" 상태 설명 없음
- 타임스탬프 포맷팅 안 됨
- 로그 레벨 구분 없음 (INFO/WARN/ERROR)

### 개선 방안

[기획자A]: 로그는 시간순 기본. 에러만 빨간색으로 강조하면 훑어보기 쉽다.
[기획자B]: 날짜 범위 + 크롤러 이름 + 상태 복합 필터가 필요. 그리고 각 로그 클릭하면 수집된 데이터 샘플도 보여줘야.
[기획자C]: CSV에 모든 필드 포함. 월간 보고서용.
→ 합의: 복합 필터 (날짜+이름+상태), 에러 강조, CSV 전체 필드, 데이터 샘플 미리보기

### 필수 기능
- P0: 날짜 범위 필터
- P0: 에러 로그 빨간색 강조
- P0: 타임스탬프 한국어 포맷 (YYYY.MM.DD HH:mm)
- P1: 로그 상세에서 수집 데이터 샘플 보기
- P1: CSV 내보내기 전체 필드 포함
- P1: "부분 성공" 상태 설명 툴팁
- P2: 실시간 로그 스트리밍 (tail -f 스타일)

## 6. 데이터 검토

### 운영자 목표
"크롤링된 데이터를 확인하고, 품질이 괜찮으면 승인하여 DB로 전달"

### 현재 문제점
- 대용량 데이터 로딩 느림 (페이지네이션 없음)
- 스키마 미리보기 50자 잘림
- 벌크 승인/거부 없음
- 품질 점수 설명 없음
- 에러 표시가 raw 객체

### 개선 방안

[기획자A]: "정상 데이터는 한 번에 승인" 기능이 핵심. 문제 항목만 빨간색으로 하이라이트.
[기획자B]: 데이터 미리보기에서 원본 크롤링 데이터를 그대로 볼 수 있어야 한다. 스키마 검증 결과도 필드별로.
[기획자C]: 승인 워크플로가 빨라야 한다. 277개 이마트 데이터를 하나하나 볼 수는 없으니까.
→ 합의: 벌크 승인 + 문제 항목 하이라이트 + 데이터 전체 미리보기 + 품질 점수 상세 설명

### 필수 기능
- P0: 페이지네이션 (대용량 데이터 대응)
- P0: 벌크 승인/거부 ("정상 전체 승인")
- P0: 데이터 전체 보기 (스크롤 가능 테이블)
- P0: 문제 항목 빨간색 하이라이트 (누락 필드, 이상치)
- P1: 품질 점수 상세 분석 (각 항목별 점수 breakdown)
- P1: 데이터 비교 (이전 크롤링 vs 현재)
- P2: 자동 승인 규칙 (품질 90% 이상이면 자동 승인)

## 공통 개선사항

### UI/UX 원칙
1. **신호등 원칙**: 녹색(정상)/노란색(주의)/빨간색(에러) 3색으로 상태 전달
2. **1클릭 원칙**: 가장 자주 하는 작업은 1클릭으로 완료
3. **한국어 우선**: 모든 UI 텍스트, 날짜 포맷, 에러 메시지 한국어

### 기술 공통
- 모든 API 호출을 client.js를 통해 통일
- 낙관적 업데이트 + 실패 시 롤백
- 로딩 스켈레톤 (스피너 대신)
- 에러 상태 한국어 메시지 + 재시도 버튼

## 7. 포레스트 레벨 크롤러 컨트롤 플레인 로드맵

### 운영자가 이해해야 하는 목표

크롤러 관리자는 "크롤러 실행 버튼 모음"이 아니라 **가격 출처를 등록하고, 증거를 모으고, AI/DB로 넘겨도 안전한지 판정하는 운영실**이어야 한다. 새 출처가 많아져도 운영자는 다음 질문에 한 화면에서 답할 수 있어야 한다.

1. 이 출처는 어디서 온 것인가?
2. 사람이 브라우저로 저장한 공개 페이지 증거가 있는가?
3. 반복 수집 주기와 담당 크롤러가 등록되어 있는가?
4. 최근 실행은 건강한가?
5. AI가 볼 원본 증거와 DB가 저장할 검증 결과가 분리되어 있는가?
6. 아직 빠진 상품/출처는 무엇인가?
7. 라이브 서비스에 연결해도 된다는 증거가 충분한가?

### 현재 기반

- `source_workbench` API와 `operator_workbench` 저장소는 운영자가 저장한 공개 HTML/JSON 증거, 출처 등록, 안전 정책을 기록한다.
- `source_runs`는 반복 실행 상태, 신규/변경/스킵 항목, `ai_handoff.json`, `manifest.json`, 원본 JSONL 증거를 만든다.
- `source_health`와 `source_coverage`는 출처 상태, 필수 증거, 미충족 항목, `source_completion_gate`를 메타데이터로 드러낸다.
- AI/DB 핸드오프 규칙은 "크롤러 원본 사실은 AI가 invent하지 않고, DB 쓰기는 승인 이후"라는 경계를 이미 문서화한다.
- 홈플러스/마트3 감사 결과처럼 등록은 되어도 검증이 얕으면 `registered_unverified`, `fixture_passing`, `blocked_by_external_key/service` 상태에 머물러야 한다.

### 구현 순서

#### 1단계: 출처 등록함을 먼저 완성

- 운영자가 이름, URL, 담당 크롤러, 수집 주기, 태그, 메모를 입력하면 "비활성 등록"으로 저장한다.
- 등록 직후 상태는 항상 `registered_unverified`로 시작한다.
- 브라우저 캡처가 필요한 출처는 운영자가 공개 페이지를 열어 HTML/JSON/HAR 요약을 저장하고, 비밀값/쿠키/개인정보는 저장하지 않게 안내한다.
- 같은 출처가 중복 등록되면 URL, 출처명, 크롤러명을 기준으로 병합 후보로 보여주고 자동 활성화하지 않는다.

#### 2단계: 증거 기반 원클릭 진단

- 등록된 출처마다 "저장한 증거로 테스트" 버튼을 제공한다.
- 테스트 결과는 `source_raw`, `parsed`, `valid`, `validation_drop`, `duplicate`, 핵심 필드 커버리지, 이미지/URL/기간/단위 누락을 숫자로 보여준다.
- 실패해도 "크롤러 실패"만 표시하지 말고 "페이지 구조 변경", "가격 없음", "권한/위치 필요", "중복만 발견"처럼 운영자가 이해할 수 있는 다음 행동을 보여준다.
- 테스트 산출물은 항상 manifest/evidence id로 남겨 AI-admin과 DB-admin이 같은 증거를 참조하게 한다.

#### 3단계: 반복 수집 후보 등록

- 증거 테스트가 통과한 출처만 반복 스케줄 후보가 된다.
- 기본값은 비활성이고, 운영자가 주기/시간대/요청 제한/max_pages/timeout을 확인해야 활성화할 수 있다.
- 마트는 매일 오전 같은 업무 주기, 핫딜은 짧은 주기, 위치/배달/마켓플레이스는 조건부 또는 수동 진단부터 시작한다.
- 스케줄 화면은 "다음 실행", "마지막 성공", "마지막 증거", "DB 전달 가능 여부"를 함께 보여준다.

#### 4단계: 출처 건강 신호등

- 초록: 최근 증거가 있고, 필수 필드 커버리지가 기준 이상이며, 승인된 반복 수집/핸드오프 조건을 만족한다.
- 노랑: 크롤은 되지만 일부 필드, 수량, 이미지, 기간, 단위, 중복률, 신선도에 주의가 있다.
- 빨강: 실패, 저장 0건, 외부 키/위치/브라우저 상태 필요, 증거 만료, DB 전달 금지.
- 회색: 등록만 되었고 아직 검증되지 않았다.
- 대시보드는 "전체 건강"보다 "운영자가 오늘 처리해야 할 출처"를 먼저 보여준다.

#### 5단계: AI/DB 핸드오프 게이트

- 크롤러는 원본 행과 증거 경로만 넘긴다. AI는 라벨/분류/매칭 후보를 제안하지만 가격, URL, 기간, 이미지 같은 원본 사실을 만들 수 없다.
- DB-admin 전달은 `ai_handoff.json`, 원본 JSONL, 품질 요약, 운영자 승인, 롤백 가능 id가 모두 있을 때만 열린다.
- 마트3처럼 공통 상품 비교가 필요한 경우, 사람이 승인한 엄격 매칭 또는 패키지/단위 일치 증거 없이는 같은 상품으로 합치지 않는다.
- 라이브 readiness 명령은 fixture/stub 성공으로 대체되지 않아야 하며, 누락된 실서비스 단계는 명시적으로 block한다.

#### 6단계: 빠진 상품/출처 발견 루프

- DB-admin/웹사이트 검색 로그, 인기 키워드, "상품 없음" 결과, 경쟁 출처 목록을 모아 누락 후보 큐를 만든다.
- 후보는 바로 크롤링하지 않고 "출처 등록 후보"로 들어간다.
- 운영자는 후보별로 공개 페이지 증거를 붙이고, 위의 진단/승인 흐름을 거쳐야 반복 수집으로 승격할 수 있다.
- 이렇게 하면 "상품이 안 보인다"는 문제를 새 크롤러 난립이 아니라 증거 있는 출처 관리 문제로 다룰 수 있다.

#### 7단계: 라이브 서비스 준비

- 라이브 전에는 bounded no-DB 진단, 제한값, 증거 id, 운영자 승인, AI 라벨링 증거, DB 최종 승인, 웹사이트 semantic API 검증이 모두 필요하다.
- HTTP 200, 빈 목록, fixture 통과, skeleton 파서 통과는 라이브 준비 증거가 아니다.
- 서비스 장애 시에는 자동 재시도보다 먼저 "DB 쓰기 중단, 증거 보존, 이전 승인 데이터 유지"가 기본 동작이어야 한다.

### 가짜 출처 완료 주장 방지 규칙

- "등록됨", "fixture 통과", "bounded diagnostic 통과", "운영자 승인", "라이브 수집 중", "DB 전달 완료"를 서로 다른 상태로 표시한다.
- UI에서 완료 배지는 `source_completion_gate.passed=true`일 때만 표시한다.
- 각 배지 옆에는 통과한 증거 id, 실행 시간, 원본 수, 파싱 수, 유효 수, DB 전달 여부를 붙인다.
- 저장 0건, `items_valid > 0`인데 `items_saved=0`, 또는 AI/DB 전달 누락은 성공이 아니라 partial/blocked로 표시한다.
- 브라우저 캡처나 fixture는 "파서 증거"일 뿐이고, 반복 라이브 수집이나 실서비스 DB 쓰기 증거로 승격하지 않는다.
- 외부 키, 로그인, 위치, CAPTCHA, 접근 제어 우회가 필요한 출처는 요구사항을 기록하되 우회 자동화로 해결하려 하지 않는다.

### 주요 리스크

- 얕은 크롤 성공을 라이브 수집 완료로 오해하면 사용자가 가짜 가격을 보게 된다.
- 마트/마켓플레이스 상품을 단위나 패키지 확인 없이 합치면 가격 비교가 틀어진다.
- 운영자 브라우저 캡처에 쿠키, 토큰, 개인정보가 섞이면 보안 사고가 된다.
- 반복 스케줄을 너무 빨리 켜면 외부 서비스 차단, 불안정한 데이터, DB 오염이 생긴다.
- AI가 원본 가격/URL/기간을 보정하도록 허용하면 출처 증거와 다른 데이터가 DB에 들어간다.
- 다른 에이전트가 마트/마켓플레이스 크롤러를 동시에 수정 중일 수 있으므로 코드 변경은 작은 단위로 잠금/소유 범위를 확인해야 한다.

### 성공 기준

- 비전문 운영자가 "출처 등록 → 증거 첨부 → 저장 증거 테스트 → 반복 후보 → 승인 → AI/DB 핸드오프" 흐름을 안내 문구만 보고 수행할 수 있다.
- 모든 출처 목록에 상태, 다음 행동, 마지막 증거, 마지막 성공, DB 전달 가능 여부가 보인다.
- 완료로 표시된 출처는 증거 id와 `source_completion_gate.passed=true`를 반드시 가진다.
- fixture/skeleton/브라우저 캡처만 있는 출처는 라이브 준비나 DB 전달 완료로 표시되지 않는다.
- mart3, Homeplus, LotteMart, marketplace skeleton은 얕은 커버리지 상태를 숨기지 않고 미충족 증거를 계속 보여준다.
- AI-admin과 DB-admin은 크롤러 결과를 원본 증거 참조와 함께 받아, 승인 전에는 public DB를 변경하지 않는다.
