# 개발 철학 (Development Philosophy)

> 이 문서는 이 프로젝트를 관통하는 개발 철학이다.
> 모든 코드 작성, 설계 결정, 테스트, 리뷰는 이 문서에 기반하여 판단한다.
> AI가 대화 기록 없이 이 문서만 읽어도 "어떤 수준으로, 어떤 방식으로" 코드를 작성해야 하는지 알 수 있어야 한다.

---

## 1. 결합도 제로 원칙 — "서로 모르는 코드"

### 의미
모든 코드 조각은 다른 코드 조각의 **존재 자체를 모르는 상태**로 작성되어야 한다.
이것은 단순히 "모듈을 분리하라"는 수준이 아니다.
파일 간, 클래스 간은 물론이고, **한 파일 안의 함수끼리조차** 가능한 한 서로에게 의존하지 않도록 작성한다.

### 왜?
기획은 반드시 바뀐다. 크게 바뀐다. 기획이 갈아엎어졌을 때 프로젝트도 함께 무너지면 안 된다.
코드 A를 수정했을 때 코드 B, C, D가 줄줄이 깨진다면, 사실상 매번 프로젝트를 새로 짜는 것과 차이가 없다.

### 구체적으로
- **모듈 간 통신은 오직 API(인터페이스)**를 통해서만. 모듈은 다른 모듈의 내부 구현을 절대 import하지 않는다.
  ```
  ✅ engine/ → core/contracts 의 인터페이스에만 의존
  ❌ engine/ → crawlers/marts/emart/crawler.py 직접 import
  ```
- **함수 하나를 수정/삭제/추가할 때**, 그 파일의 다른 함수를 함께 고칠 필요가 없어야 한다.
  함수는 자기 할 일만 하고, 다른 함수의 내부 구현에 의존하지 않아야 한다.
  만약 함수 B가 함수 A의 내부 로직을 알아야 동작한다면, 그것은 결합이다.
- **어떤 코드를 변경할 일이 생겼을 때**, 해당 부분"만" 건드리면 끝나야 한다.
  파일 전체를 이해하지 않아도, 관련된 특정 부분만 읽고 수정할 수 있는 구조여야 한다.
- 모듈 간 통신은 **EventBus**(비동기 이벤트) 또는 **REST API 호출**로만 이루어진다.
  모듈은 "누가 이 이벤트를 받는지"를 모른다. 그냥 이벤트를 발행할 뿐이다.

### 실패 예시
```python
# ❌ BAD: storage가 engine의 내부 구현을 안다
from engine.executor import StrategyExecutor
executor = StrategyExecutor(...)
result = executor._internal_method()  # 내부 메서드 직접 사용

# ✅ GOOD: 계약(인터페이스)만 안다
from core.contracts.engine import EngineContract
def save_result(engine: EngineContract, ...):
    result = engine.execute(...)  # 계약에 정의된 메서드만 사용
```

## 2. 확장성 — "미래의 코드를 위한 자리를 남겨라"

### 의미
지금 작성하는 코드는 "현재 기능"만 구현하되, 그 구조는 "아직 존재하지 않는 기능"이
추가될 수 있도록 열려 있어야 한다.
이것은 미래의 기능을 미리 구현하라는 뜻이 아니다.
**미래의 기능이 들어올 자리를 막지 말라는 뜻이다.**

### 구체적으로
- 새로운 크롤러가 추가된다 → 폴더 하나 만들고 파일 넣으면 끝. 기존 코드 변경 0줄.
- 새로운 전략이 추가된다 → BaseStrategy 상속받아 구현하면 끝. 엔진 코드 변경 0줄.
- 핫딜 게시판이 5개에서 50개로 늘어난다 → 플러그인 50개 등록하면 끝. 코어 코드 변경 0줄.
- DB 스키마가 완전히 바뀐다 → 마이그레이션 스크립트만 짜면 끝. API 코드 변경 최소.
- 프론트엔드 탭이 추가된다 → 새 탭 컴포넌트만 추가. 기존 탭 코드 변경 0줄.

### Open-Closed Principle
소프트웨어 설계 원칙 중 "개방-폐쇄 원칙"이 이것을 정확히 표현한다:
- **확장에는 열려 있고** (새 기능을 추가할 수 있고)
- **수정에는 닫혀 있다** (기존 코드를 고칠 필요 없다)

하드코딩된 if-else 분기, 특정 클래스명을 직접 참조하는 코드, 고정된 설정값 등은
확장성을 막는 대표적인 안티패턴이다.

## 3. 오류 기록 — "같은 실수를 반복하지 않기 위한 장치"

### 의미
개발 중 발생하는 모든 오류, 잘못된 접근 방법, 삽질한 내용을 **별도 파일에 기록**하고,
그 기록을 지속적으로 업데이트하며 읽어야 한다.

### 왜?
- 같은 에러를 두 번 디버깅하는 것은 시간 낭비다.
- AI가 대화를 넘겨서 작업할 때, 이전에 어떤 접근이 실패했는지를 모르면 같은 삽질을 반복한다.
- 면접에서 "어떤 문제를 만났고, 어떻게 해결했는가"를 구체적으로 답할 수 있다.

### 기록 형식 (`ERROR_LOG.md`)
```markdown
## [2026-03-18] Windows cp949 인코딩 문제
- **증상**: 콘솔에서 한국어 크롤링 데이터가 깨짐
- **원인**: requests 라이브러리가 응답 인코딩을 잘못 추론 (UTF-8인데 ISO-8859-1로 인식)
- **잘못된 접근**: print 함수에 encoding 파라미터를 추가하려 함 → 근본 원인 아님
- **해결**: response.encoding = "utf-8" 명시적 설정 + sys.stdout UTF-8 래핑
- **교훈**: requests의 .text는 .encoding에 의존한다. 한국어 사이트는 항상 encoding을 명시하라.
```

### 규칙
- 에러가 발생할 때마다 즉시 기록한다 (나중에 하면 잊어버린다).
- "해결됨"으로 끝내지 말고, **왜 그 접근이 잘못됐는지**, **근본 원인이 뭐였는지**까지 적는다.
- AI가 새 세션을 시작하면, 이 파일을 먼저 읽고 시작한다.

## 4. 플러그인 아키텍처 — "서버를 끄지 않고 기능을 바꾸는 구조"

### 의미
모든 기능은 **플러그인**으로 만든다.
"플러그인"이라 함은, 독립된 파일/폴더를 추가하거나 삭제하는 것만으로 기능이 추가/제거되며,
이것이 다른 어떤 코드에도 영향을 주지 않는 구조를 말한다.

### 범위
이것은 백엔드 로직에만 적용되는 것이 아니다.

| 영역 | 플러그인 구조 |
|---|---|
| 크롤러 | `crawlers/marts/emart/` 폴더 추가 = 이마트 크롤러 활성화 |
| 전략 | `engine/strategies/new_st.py` 파일 추가 = 새 전략 활성화 |
| API 라우트 | `api/routes/new_route.py` 추가 = 새 엔드포인트 활성화 |
| 프론트 탭 | 탭 컴포넌트 추가 = 새 탭 UI 활성화, 기존 탭 코드 변경 없음 |
| **CSS조차** | 테마/컴포넌트 CSS 파일 교체로 디자인 변경 가능 |

### 프론트엔드도 예외 없다
프론트엔드의 CSS, UI 컴포넌트도 플러그인처럼 독립적이어야 한다.
- 물가비교 탭의 CSS를 수정해도 핫딜 탭에 영향 없어야 한다.
- 새 탭을 추가해도 기존 탭 코드를 건드릴 필요 없어야 한다.
- CSS는 컴포넌트별로 분리하고, 전역 스타일은 CSS 변수(디자인 토큰)로만 관리한다.

### 핫 리로드를 고려한 설계
추후 기능 추가가 잦을 것이다. 매번 서버를 껐다 켜는 것도 비용이다.
가능한 한 서버 재시작 없이 새 기능이 로드되는 구조를 지향한다.
(FastAPI의 auto-reload, 플러그인 동적 발견 등)

## 5. 의존성 주입 & 지속적 통합 (DI / CI)

### 의존성 주입 (DI)
- 모든 구체 클래스의 조립은 **`container.py` 한 곳**에서만 수행한다.
- 나머지 코드는 인터페이스(계약)만 알고, 구체 구현체가 뭔지 모른다.
- 테스트에서는 실제 구현 대신 Mock을 주입할 수 있다. 이것이 DI의 핵심 이점이다.
- 이 구조 덕분에 PostgreSQL을 SQLite로 바꾸든, requests를 httpx로 바꾸든,
  **바꿔야 할 곳은 container.py 한 곳뿐이다.**

### 지속적 통합 (CI)
- 모든 커밋에 대해 자동으로 전체 테스트가 돌아가야 한다.
- 테스트가 깨지는 커밋은 머지할 수 없다.
- 이것을 위해 테스트는 항상 **빠르고, 독립적이고, 반복 가능**해야 한다.
- 네트워크에 의존하는 테스트는 VCR 카세트 등으로 녹화/재생하여 오프라인에서도 돌아가게 한다.

## 6. 다층 테스트 전략 — "테스트가 있으면 마음 놓고 고친다"

### 의미
코드를 자신 있게 수정하려면, 수정해도 기존 기능이 안 깨진다는 **보증**이 있어야 한다.
그 보증이 테스트다. 테스트가 없으면 모든 수정이 도박이다.

### 테스트 종류

| 종류 | 무엇을 보는가 | 예시 |
|---|---|---|
| **단위 테스트 (Unit)** | 함수/클래스 하나가 올바르게 동작하는가 | `StrategyExecutor`가 전략을 difficulty순으로 정렬하는가 |
| **화이트박스 테스트** | 내부 로직 분기가 올바른가 (코드를 알고 테스트) | 에러 타입별 분기 처리가 맞는가, 경계값 처리 |
| **블랙박스 테스트** | 입력 → 출력만 보고, 기대하는 결과가 나오는가 | URL을 넣으면 핫딜 목록이 나오는가 |
| **통합 테스트** | 여러 모듈이 함께 동작할 때 문제가 없는가 | 크롤러→엔진→저장소 전체 파이프라인 |
| **리그레션 테스트** | 이전에 통과했던 테스트가 여전히 통과하는가 | 전체 test suite 실행 |
| **실사용 테스트** | 실제 환경에서 실제 데이터로 기대대로 동작하는가 | 실제 웹사이트에 HTTP 요청 보내고 결과 확인 |

### 핵심: 테스트는 모아둔다
- 모든 테스트 코드는 정리된 구조로 보관한다.
- 언제든 `pytest`를 돌리면 전체 프로젝트의 건강 상태를 확인할 수 있다.
- 새 기능을 추가할 때, 기존 테스트가 깨지면 즉시 알 수 있다.
- 이것이 **리그레션 테스트**이고, 프로젝트가 커질수록 이 가치는 기하급수적으로 커진다.

## 7. TDD — "테스트가 먼저, 코드가 나중"

### 개발 순서
1. **Red** — 아직 없는 기능의 테스트를 먼저 작성한다. 당연히 실패한다.
2. **Green** — 테스트를 통과하는 최소한의 코드를 작성한다.
3. **Refactor** — 코드를 깔끔하게 정리한다. 테스트가 여전히 통과하는지 확인한다.
4. 반복.

### 왜 TDD인가
- 테스트를 나중에 작성하면, 바쁠 때 생략하게 된다. 결국 테스트 없는 코드가 쌓인다.
- 테스트를 먼저 작성하면, "이 코드가 뭘 해야 하는지"를 먼저 정의하게 된다.
  이것은 설계를 강제하는 효과가 있다.
- TDD로 작성된 코드는 자연스럽게 테스트 가능한(testable) 구조가 된다.
  테스트 불가능한 코드 = 결합도가 높은 코드 = 나쁜 코드.

## 8. 실제 검증 — "돌아가는 것"과 "제대로 동작하는 것"은 다르다

### 의미
모듈이 완성되면 반드시 **실제 데이터로, 실제 환경에서** 테스트한다.
"pytest가 통과했으니 끝"이 아니다.

### 백엔드 검증 원칙
- 크롤러가 완성되면, **실제 웹사이트에 요청을 보내서 실제 데이터를 받아온다.**
- 받아온 데이터가 "쓸 수 있는 데이터"인지 확인한다:
  - 한국어가 깨지지 않았는가?
  - 가격 정보가 파싱 가능한 형태인가?
  - 이 데이터가 나중에 "물가 평균 계산", "핫딜 가격 비교"에 실제로 쓸 수 있는 구조인가?
- **기능 명세를 기반으로 검증한다.** "이 크롤러의 데이터는 추후 어디에, 어떻게 쓰일 것인가?"
  를 이해하고, 그 쓰임에 적합한 결과가 나오는지 확인한다.

### 프론트엔드 검증 원칙
AI는 프론트엔드의 **시각적 결과물을 직접 볼 수 없다.** 콘솔에 출력되는 것이 아니기 때문이다.
이것은 프론트엔드 개발에서 가장 큰 맹점이다.
따라서 다음을 반드시 수행한다:

1. **브라우저 스크린샷 검증** — 브라우저에서 실제로 열어 스크린샷을 찍고, UI가 의도대로
   렌더링되었는지 확인한다.
2. **상호작용 테스트** — 호버, 클릭, 스크롤, 탭 전환 등의 인터랙션이 올바르게 동작하는지
   직접 테스트한다.
3. **디버그 로그 삽입** — 사용자 상호작용의 각 구간에 `console.log`를 삽입하여,
   동작 흐름과 상태를 콘솔에서 추적할 수 있게 한다.
   ```javascript
   // 예시: 자동완성 동작 디버그
   console.log(`[검색] 입력: "${query}", 매칭: ${results.length}건`);
   console.log(`[탭전환] ${prevTab} → ${nextTab}`);
   console.log(`[차트] ${product.name} 30일 데이터 렌더링 완료`);
   ```
4. **시각 검증 체크리스트** — 다음 항목을 항상 확인한다:
   - 요소가 잘리거나 가려지지 않는가
   - 반응형에서 레이아웃이 깨지지 않는가
   - 호버/포커스 상태가 올바르게 표시되는가
   - 오버레이/모달이 올바른 z-index로 표시되는가
   - 애니메이션/트랜지션이 부드럽게 동작하는가
   - 스크롤 시 헤더가 올바르게 고정되는가
   - 자동완성 드롭다운이 올바른 위치에, 올바른 크기로 표시되는가

### 검증 기록
모든 검증 결과는 기록한다. "해봤는데 됨"이 아니라:
- 무엇을 테스트했는가
- 어떤 입력을 넣었는가
- 어떤 결과가 나왔는가
- 기대와 일치하는가
- 일치하지 않으면 무엇이 문제였고 어떻게 고쳤는가

---

## 9. 디버깅 가시성 — "문제를 빨리 찾을 수 있는 코드"

### 의미
문제가 발생했을 때, **어디서 무슨 문제가 생겼는지**를 빠르게 찾을 수 있어야 한다.
이것은 에러 메시지를 잘 작성하는 것 이상의 문제다.

### 구체적으로
- **로깅**: 모든 주요 동작에 적절한 수준의 로깅을 넣는다.
  - INFO: 크롤링 시작/완료, 전략 전환, 데이터 저장
  - WARNING: 예상 밖의 응답, fallback 발동, 느린 응답
  - ERROR: 실패, 예외, 데이터 손실
  - DEBUG: 상세 흐름, 변수 값, HTTP 헤더

- **에러 분류**: 에러를 단순히 "실패"로 처리하지 않는다.
  "왜 실패했는가"를 에러 타입으로 분류한다 (IP 차단, CAPTCHA, DOM 변경, 타임아웃 등).
  이것이 `DiagnosticsEngine`과 `ErrorType` 열거형의 존재 이유다.

- **프론트엔드 디버그 콘솔**: JavaScript 코드에도 구간별로 `console.log`를 삽입한다.
  사용자에게는 보이지 않지만, 개발자 도구에서 동작 흐름을 추적할 수 있다.

- **실패 체인 기록**: 크롤링이 실패했을 때, 어떤 전략이 어떤 순서로 시도되었고,
  각각 어떤 이유로 실패했는지를 전부 기록한다 (이것이 `StrategyFailure` 리스트).

## 10. 프로덕션 마인드셋 — "이것은 졸업작품이 아니라 실제 서비스다"

### 의미
이 프로젝트는 실제로 인터넷에 올려서 서비스할 계획이다.
따라서 모든 코드는 **"배포해도 괜찮은가?"** 를 기준으로 판단한다.
"기능은 되는데 서비스하면 문제가 생기는" 상태는 **미완성**이다.

### "작동한다"만으로는 부족한 것들

| 영역 | "작동함"의 함정 | 프로덕션 기준 |
|---|---|---|
| **보안** | SQL Injection이 가능하지만 기능은 된다 | 모든 입력은 검증/이스케이프 |
| **동시성** | 혼자 쓸 때는 되지만 10명이 동시에 쓰면 깨진다 | 동시 접속 고려한 설계 |
| **에러 처리** | 에러 나면 500 Internal Server Error | 사용자에게 의미 있는 에러 메시지 |
| **성능** | 느리지만 결국 응답은 온다 | 3초 이내 응답 목표 |
| **데이터 무결성** | 크롤링 중 서버가 죽으면 데이터가 반만 저장됨 | 트랜잭션으로 원자성 보장 |
| **로깅** | 에러가 나도 로그가 없어서 원인을 모른다 | 구조화된 로깅, 에러 추적 |
| **환경 분리** | 개발 DB와 프로덕션 DB가 같다 | dev/staging/prod 환경 분리 |
| **비밀 관리** | API 키가 코드에 하드코딩 | .env 파일, 절대 Git 커밋 안 함 |

### TDD 케이스도 "크게" 본다
테스트 케이스를 설계할 때, "이 함수가 올바른 값을 반환하는가"만 보지 않는다.
- 동시에 여러 크롤러가 돌면 어떻게 되는가?
- 네트워크가 불안정할 때는?
- 데이터가 예상과 다른 형태로 들어오면?
- 악의적인 입력이 들어오면?
- 디스크가 가득 차면?
- 하루에 10만 건이 쌓이면 DB 쿼리가 느려지지 않는가?

이런 질문을 테스트 설계 단계에서부터 던져야 한다.

## 11. 문서화 — "코드가 아닌 맥락도 전달하라"

### 의미
코드만으로는 "왜 이렇게 했는가"를 알 수 없다.
결정의 이유, 대안으로 고려했던 것, 포기한 접근법, 주의사항 등은
**코드 밖, 문서에** 기록해야 한다.

### 이 프로젝트의 문서 체계

| 문서 | 역할 |
|---|---|
| `TECH_SPEC.md` | 전체 프로젝트 기획서. 아키텍처, 대상, DB, API, 진행 현황 |
| `DEV_PHILOSOPHY.md` | 이 문서. 개발 원칙과 철학 |
| `ERROR_LOG.md` | 발생한 오류, 원인, 해결 과정 기록 |
| 각 모듈 docstring | 해당 모듈이 무엇을, 왜, 어떻게 하는지 |

### AI 핸드오프 기준
대화 기록이 모두 유실되더라도, 이 문서들만 있으면:
1. 프로젝트가 무엇인지 안다 (`TECH_SPEC.md`)
2. 어떻게 코드를 작성해야 하는지 안다 (`DEV_PHILOSOPHY.md`)
3. 어디까지 했고 무엇이 남았는지 안다 (`TECH_SPEC.md` 진행 현황)
4. 과거에 어떤 실수가 있었는지 안다 (`ERROR_LOG.md`)

## 12. 요약: 이 철학이 달성하려는 것

**"언제든 어떤 부분이든 자신 있게 고칠 수 있는 프로젝트."**

- 기획이 바뀌어도 → 플러그인 교체로 해결 (원칙 1, 2, 4)
- 버그가 터져도 → 에러 타입 자동 분류 + 로그로 즉시 파악 (원칙 3, 9)
- 코드를 수정해도 → 테스트가 지켜주니까 안심하고 수정 (원칙 6, 7)
- AI가 바뀌어도 → 문서가 모든 맥락을 전달 (원칙 3, 11)
- 서비스에 올려도 → 프로덕션 수준으로 작성했으니까 안심 (원칙 10)
- 기능이 추가되어도 → 확장성 있는 구조니까 기존 코드 변경 없이 추가 (원칙 2, 4)

이 원칙들은 서로 독립적이지 않다. 서로 강화한다.
결합도가 낮아야 테스트가 쉽고, 테스트가 있어야 리팩토링이 안전하고,
리팩토링이 안전해야 확장이 가능하고, 확장이 가능해야 기획 변경에 대응할 수 있다.

**하나라도 빠지면 나머지가 무너진다. 전부 지켜야 한다.**
