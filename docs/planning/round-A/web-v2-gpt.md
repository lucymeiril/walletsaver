# Web 영역 v2 적대적 검토 (GPT-5.5, Round-A)

> 입력: `docs/planning/round-A/web-v1-opus.md`  
> 범위: 사용자/회원 프론트, Public/게시판 API 확인  
> 원칙: v1을 고치지 않고, 빠진 것·모순·숫자 불일치·운영 구멍을 바로 찌른다.

---

## A. 본문 요약 — v1을 이렇게 이해했다

v1의 큰 방향은 맞다. WalletSavior 웹은 “초심자도 바로 이해하고, 핫딜러는 더 깊게 파고드는” 화면이어야 하며, 현재 코드는 홈/검색/카테고리/상품상세/게시판/회원/주유소 일부가 뼈대로 존재한다. v1은 이 뼈대 위에 다음을 얹자는 초안이다.

1. 홈을 단순 상품 그리드에서 `진짜 핫딜 TOP / 내 주변 / 카테고리 / 인기 게시글` 구조로 바꾼다.
2. 상품 상세에 라벨, 게이지, 가격 추이, 마트별 가격표, 도매가/적정가, 관련 게시글, 핫딜러 패널을 넣는다.
3. 게시판은 핫딜/자유 게시판을 유지하되 카드형 목록, 인라인 이미지 삽입, 상품 자동 매칭, 가격 등급 미리보기를 넣는다.
4. `직접 해먹기 vs 식당` 비교 조합기 페이지를 새로 만든다.
5. 초심자/핫딜러 모드를 토글로 양립시킨다.
6. 즐겨찾기, 마이페이지, 모바일 CSS, 플러그인/iframe 자리를 잡는다.
7. 식당, 알림, 소셜 로그인, 실제 플러그인 로더는 v1.5 이후로 미룬다.

내 판단: v1은 “숲”으로는 좋지만, 한 화면에 너무 많이 쌓고, 숫자 산식과 검증 흐름을 덜 정의했다. 특히 “복잡하지 않게”라는 헌법과 상품 상세 7블록이 정면충돌한다.

### B-2. 5대 공백 진단 검증

v1의 5대 공백은 대체로 맞다.

1. **상품 상세 가격 추이/도매가/마트 가격 컬럼 없음** — 정확함. 단, 도매가는 DB/API 모델도 비어 있어 “회색 자리”가 아니라 “언제 어떤 데이터로 채울지”를 먼저 정해야 한다.
2. **게시판 글쓰기 인라인 이미지·상품 자동매칭 부재** — 정확함.
3. **비교 조합기·식당 페이지 부재** — 정확함.
4. **초심자/핫딜러 모드 토글 없음** — 정확함.
5. **모바일 분기 거의 없음** — 정확함. 인라인 style이 대부분이고 전역 CSS/import도 없다.

추가로 v1이 놓친 현재 공백 3개:

- `/fuels` 페이지 파일은 있는데 라우트가 없어 홈의 주유소 카드가 실제로는 깨질 수 있다.
- `ProductDetailPage`의 `PriceGauge`에 `currentPrice={pg.p50}`가 들어간다. 즉 “현재가” 위치가 평소가(P50)로 찍힐 가능성이 있다. 애초에 상품 상세 API에 현재가 필드가 없다.
- 검색 결과의 “핫딜가”는 현재 최저 관측가가 아니라 P10 분위값이다. 사용자는 “지금 이 가격에 살 수 있다”고 오해할 수 있다.

## C. v1 핵심 약점 12개

### 1. 상품 상세 7블록은 “복잡하지 않게”와 충돌한다

v1 상품 상세는 라벨, 게이지, 추이, 마트표, 도매가, 관련글, 핫딜러 패널, 즐겨찾기/알림/글쓰기 버튼까지 사실상 8~9덩어리다. 초심자에게 “한 눈에”가 아니라 “보고서”처럼 보일 수 있다.

구체 대안:

- 기본 화면은 **3블록**으로 고정한다.
  1. 결론 카드: `지금 살만함 / 보통 / 비쌈` + 평소 대비 숫자 + 대표 마트
  2. 어디서 사나: 마트별 현재가 카드/표
  3. 사람들이 뭐라 하나: 관련 게시글 + verdict 요약
- 게이지/추이/도매가/표본/시즌보정은 **“근거 자세히 보기” 한 영역**으로 묶는다.
- 핫딜러 모드 ON일 때만 그 근거 영역을 펼친 상태로 시작한다.
- 회색 자리표시 블록을 여러 개 항상 보이게 두지 않는다. 빈 블록이 많으면 “서비스가 덜 만든 느낌”이 먼저 온다.

### 2. “평소 대비 -X%” 산식이 정의되지 않았다

v1은 카드/상세/글쓰기에서 모두 `평소 대비 -X%`를 쓰자고 하지만 X의 기준이 없다. 현재 `ProductCard`는 `(P50 - P10) / P50`로 할인율을 계산한다. 그런데 사용자가 글쓰기에서 입력하는 `deal_price`는 P10이 아니다. 상품 상세에는 현재가 필드도 없다.

이대로 가면:

- 카드: P10 기준 -32%
- 상세: 현재 마트가 기준 -20%
- 글쓰기: 사용자가 입력한 가격 기준 -40%

처럼 같은 상품에 숫자 3개가 뜬다.

구체 대안:

- 용어를 분리한다.
  - `핫딜 기준가`: P10
  - `평소가`: P50
  - `지금 최저가`: 현재 구매 가능한 최저 가격
  - `제보가`: 게시글 작성자가 입력한 가격
- 할인율 공식은 하나로 고정한다: `(평소가 P50 - 표시가격) / 평소가 P50`.
- “표시가격”이 무엇인지 화면마다 라벨로 박는다: `지금 최저가 기준`, `제보가 기준`, `핫딜 기준가 기준`.
- 표본 부족이면 `-X%`를 숨기고 `표본 3건: 숫자 참고용`처럼 표시한다.

### 3. 글쓰기 등급 자동 표시는 조작/오용 경로가 있다

v1은 `canonical_id 자동 매칭 + deal_price 입력 → 🔥핫딜 라벨 자동 표시`를 제안한다. 좋은 기능이지만 현재 구조에서는 작성자가 아무 가격이나 넣어도 라벨이 붙는다. `deal_url`은 단순 문자열 저장이고, URL의 마트/상품/가격이 `canonical_id`, `deal_price`, `mart_name`과 맞는지 확인하지 않는다.

구체 시나리오:

- 작성자가 두부 상품을 매칭하고 가격을 100원으로 입력한다.
- 시스템은 P10보다 낮으니 “진짜 핫딜!”을 붙인다.
- 링크는 다른 상품이거나 빈 값이어도 글은 올라간다.

구체 대안:

- 자동 라벨 옆에 출처를 붙인다: `작성자 입력가 기준`.
- `deal_url`이 없으면 `링크 없음`을 크게 노출한다.
- URL 도메인과 `mart_name`이 다르면 등록 전 경고 문구가 아니라 글 상단에 `마트명/링크 불일치` 배지를 붙인다.
- 링크 가격 파싱은 v1 필수까지는 아니어도, 최소한 `공식몰 링크 / 기타 링크 / 링크 없음` 3분류는 v1에 넣어야 한다.

### 4. 비교 조합기 v1 진입은 사용자 검증이 없다

사용자가 “직접 해먹기 vs 식당 가격 비교”를 명시했으니 빼면 안 된다. 다만 v1이 그린 비교 조합기는 사용자가 식재료를 검색하고 수량을 조정하고 식당 메뉴를 고르는 구조다. “최소 노력”과 충돌한다.

구체 대안:

- v1에서 `/compare`를 만들되, 빈 계산기보다 **프리셋 중심**으로 시작한다.
  - 김치찌개
  - 된장찌개
  - 제육볶음
  - 샐러드
- 사용자는 “김치찌개 2인분”만 고르면 기본 재료가 자동으로 들어간다.
- 핫딜러 모드에서만 재료 수량/마트 가중치/단위가를 상세 조정한다.
- 식당 데이터가 없으면 “직접 만들기 예상가”만 보여주지 말고, 사용자가 직접 식당 가격을 입력해 비교하게 한다. 이러면 네이버 연동 전에도 기능이 죽지 않는다.

### 5. 부분 모바일 대응은 더 나쁜 결과를 만들 수 있다

v1은 글로벌 CSS 1장 + 미디어쿼리 4종으로 핵심 페이지를 손보자고 한다. 방향은 맞지만, 일부 페이지만 좋아지고 나머지는 그대로이면 사용자는 “어떤 페이지는 앱 같고 어떤 페이지는 깨짐”으로 느낀다.

구체 대안:

- 별도 모바일 SPA를 만들 필요는 없다. 반응형 단일 앱이 맞다.
- 대신 v1의 모바일 기준을 “페이지별”이 아니라 **공통 컴포넌트별**로 잡는다.
  - 카드 그리드
  - 상단 검색
  - 표 → 카드/가로스크롤
  - 필터 → 바텀시트/접힘
  - 폼 입력
- 위 5개 공통 패턴을 먼저 만들면 홈/검색/상세/게시판/글쓰기/주유소가 같이 좋아진다.

### 6. 초심자/핫딜러 토글은 말보다 운영이 어렵다

v1은 `.pro-only`로 숨기면 된다고 했지만 실제 문제는 CSS가 아니라 정보 구조다. 핫딜러 모드에서 배송비 포함 단위가, 시즌 보정, 마트 가중치 슬라이더, 다중 추이 그래프까지 열면 API/상태/테스트가 두 배가 된다.

구체 대안:

- 모드는 2개로 유지하되, v1의 핫딜러 기능을 3단계로 나눈다.
  1. v1: P10/P25/P50/P75, 표본 수, 단위가
  2. v1.5: 다중 마트 추이, 배송비 포함
  3. v2: 마트 가중치, 시즌 보정 조정
- “핫딜러 상세조정”은 제거하지 않는다. 다만 첫 구현은 조정값 2~3개로 시작해야 실제로 굴러간다.

### 7. 게시판 인라인 이미지 보안/추적 문제가 설계에 없다

현재는 업로드 이미지를 서버에 저장하고 `[[img:N]]`를 ReactMarkdown 이미지로 치환한다. v1의 인라인 이미지 UX 개선은 맞다. 추가로 정해야 할 점이 있다.

구체 시나리오:

- 마크다운 본문에 외부 이미지 URL을 직접 넣으면, 글을 보는 사람의 브라우저가 외부 호스팅 서버에 접속한다. 외부 서버는 IP/브라우저 정보를 볼 수 있다.
- ReactMarkdown 기본 렌더링을 그대로 쓰면 링크/이미지 정책이 느슨해질 수 있다.

구체 대안:

- 에디터의 “이미지 삽입”은 서버 업로드 이미지만 기본으로 넣는다.
- 외부 이미지 URL을 본문에 직접 쓴 경우에는 `외부 이미지` 배지를 붙이거나 링크로만 표시한다.
- HTML 직접 입력은 렌더하지 않는 지금 방향을 유지한다.
- 이미지 파일 확장자만 보지 말고 실제 MIME/크기 제한을 표시한다. 사용자에게는 “사진은 10장, 장당 5MB”처럼 쉽게 보이면 된다.

### 8. 즐겨찾기/알림이 v1에서 약하면 재방문 동기가 없다

v1은 즐겨찾기를 1단계에 넣고 알림은 v1.5로 미룬다. 그런데 WalletSavior는 매일 가격이 바뀌는 서비스다. 재방문 이유가 없으면 사용자는 한 번 검색하고 끝난다.

구체 대안:

- v1에 최소 알림까지 넣을 필요는 없더라도 **즐겨찾기 후 재방문 화면**은 반드시 필요하다.
- `/account`에 `내가 찜한 상품`, `최근 본 상품`, `찜한 카테고리 오늘 핫딜` 탭을 둔다.
- 가격 알림은 v1.5여도, v1에서 `알림 받을 가격` 입력 UI 자리는 상품 상세에 넣는다. 저장이 안 되면 안 된다. 저장까지는 되어야 한다.

### 9. 식당 페이지를 v1.5+로 미루는 논리는 반쯤만 맞다

네이버 플레이스 본격 연동을 미루는 건 현실적이다. 하지만 사용자가 위치 기반 식당과 직접 해먹기 비교를 핵심으로 말했기 때문에, 식당 영역을 “준비 중” 페이지만 두면 기대를 깬다.

구체 대안:

- v1 식당은 외부 연동 없이도 동작해야 한다.
  - 사용자가 식당 메뉴 가격을 직접 입력
  - 자주 쓰는 메뉴 프리셋
  - 지역 평균이 없으면 “내 입력값 기준 비교”
- `/restaurants`는 빈 자리보다 “오늘은 직접 해먹는 게 싼가?”로 `/compare`에 합쳐도 된다.
- 즉 식당은 데이터 연동을 미루되, 사용자 행동 흐름은 v1에 있어야 한다.

### 10. 플러그인/iframe은 v1 누락에 가깝다

v1은 플러그인/iframe을 G장에서 다루지만 “컴포넌트 인터페이스 정리, 실제 loader는 v1.5~v2”로 둔다. 사용자가 플러그인(iframe)을 핵심 기능으로 명시했다면 이것은 너무 약하다.

구체 대안:

- v1에서 거대한 플러그인 마켓을 만들 필요는 없다.
- 하지만 `iframe 위젯 슬롯 1개`는 실제 동작해야 한다.
  - 예: 상품 상세 하단 `외부 가격 계산기/가계부 위젯 슬롯`
  - 허용된 URL 목록 기반
  - postMessage 이벤트 타입 2~3개만 정의
- 이 정도가 있어야 “향후 가능”이 아니라 “핵심 구조가 이미 있음”이 된다.

### 11. 회원가입/로그인은 OAuth vs 자체를 운영 관점으로 다시 봐야 한다

현재 자체 이메일/비밀번호 가입은 동작한다. v1은 소셜 로그인을 v1.5로 미룬다. 이 결정은 개발비 관점에서는 맞지만, 운영 관점에서는 가입 전환율 문제가 생긴다.

구체 질문:

- 핫딜 글쓰기/댓글/즐겨찾기를 하려면 가입이 필요한데, 사용자가 이메일 가입을 감수할 만큼 동기가 충분한가?
- 초기 운영자가 비밀번호 문의, 계정 분실, 이메일 오타를 처리할 준비가 있는가?
- 카카오/네이버 중 하나만 먼저 붙이면 한국 사용자 진입 장벽이 얼마나 내려가는가?

구체 대안:

- v1: 자체 로그인 유지 + 비로그인 즐겨찾기 로컬 저장 허용
- v1.5: 카카오 또는 네이버 1개 우선
- 비밀번호 재설정 메일이 없으면 자체 가입은 “가입은 되는데 잃어버리면 끝”이므로, 자체 로그인을 계속 쓸 거면 재설정 흐름이 소셜보다 먼저일 수 있다.

### 12. 라이트/다크, 접근성, i18n이 v1에서 거의 빠졌다

현재 코드는 인라인 스타일 중심이고 색상 토큰이 없다. aria는 일부 있다. i18n 구조는 없다.

구체 대안:

- 라이트/다크: v1에서 완전한 테마 시스템까지는 아니어도 CSS 변수(`--bg`, `--text`, `--card`, `--accent`)를 먼저 깐다. 그래야 나중에 전체 색상을 갈아엎지 않는다.
- 접근성: 검색, 필터, 모달/바텀시트, 라디오 버튼, 표의 모바일 변환에 키보드 이동 기준을 둔다. “예쁘게”보다 “눌리는지”가 먼저다.
- i18n: 당장 다국어 UI를 만들 필요는 없지만, 가격/단위/날짜 포맷 함수는 한 곳으로 모은다. 지금은 각 컴포넌트가 `toLocaleString`을 따로 쓴다.

## D. v1이 사용자 헌법/명시 기능에서 빠뜨리거나 약하게 둔 부분

| 사용자 명시 기능 | v1 반영 | v2 판단 |
|---|---|---|
| 핫딜 게시판/자유 게시판 | 반영 | 정확함. 실제 코드도 존재. |
| 카테고리 지정 | 반영 | DB 카테고리 + 자유 카테고리 병존은 좋다. 다만 자유 태그 클릭 필터 API가 현재 없다. |
| 인라인 이미지 | 반영 | 방향은 맞다. 외부 이미지/업로드 이미지 정책을 같이 정해야 한다. |
| 적정 핫딜가 제시 | 반영 | P10/P50 기반으로는 가능하나 “현재가/제보가/핫딜 기준가” 용어 분리가 먼저다. |
| “이거 진짜 핫딜?” 댓글 | 반영 | verdict 3종은 좋다. 글 상단에 더 크게 올리는 것도 맞다. |
| 위치 기반 주유소 | 반영 | 페이지 파일/API는 있으나 `/fuels` 라우트가 빠져 현재 진입이 깨진다. |
| 위치 기반 식당 | v1.5로 미룸 | 외부 연동은 미뤄도 사용자 입력 기반 비교 흐름은 v1에 있어야 한다. |
| 직접 해먹기 vs 식당 가격 비교 | 반영 | 빈 계산기보다 프리셋형으로 시작해야 초심자가 쓴다. |
| 옷 쇼핑몰 할인 | 거의 없음 | v1 카테고리/게시판 예시에 의류가 살짝 있지만, 실제 상품 도메인은 마트 식료품 중심이다. “의류 핫딜은 게시판 중심으로 먼저 받는다” 같은 위치 지정이 필요하다. |
| 배달 진짜 핫딜인지 | 없음 | 식당/배달을 v1.5로 미루더라도, 게시판 카테고리나 비교 조합기 입력값으로 받을 자리는 있어야 한다. |
| 플러그인(iframe) | 자리만 | 핵심 명시 기능치고 약하다. v1에 실제 iframe 슬롯 1개는 있어야 한다. |
| 핫딜러 상세 조정 | 반영 | 방향은 맞다. 다만 v1에서 너무 많은 조정값을 한꺼번에 열면 구현/테스트가 늘어진다. 단계화가 필요하다. |
| “복잡하지 않게” | 선언은 강함 | 상품 상세 7블록, 비교 조합기 수동 입력, 핫딜러 기능 과다로 실제 설계가 흔들린다. |
| “초심자 쉽게” | 선언은 강함 | canonical_id 수동 입력, 이미지 마커 수동 입력 같은 현재 문제를 잘 잡았다. 추가로 프리셋/자동완성이 더 필요하다. |

핵심 누락 결론:

1. **의류/배달 핫딜**은 v1에서 위치가 없다. 전용 크롤링이 아니더라도 게시판 카테고리와 글쓰기 필드에서 받을 수 있어야 한다.
2. **플러그인/iframe**은 “나중에”가 아니라 v1에 최소 동작 슬롯이 필요하다.
3. **식당/배달**은 외부 데이터 연동을 미뤄도 사용자 입력형 비교는 v1에 넣어야 한다.
4. **즐겨찾기 후 재방문**이 약하다. 알림을 미뤄도 찜한 상품/카테고리 기반 홈 섹션은 필요하다.
5. **숫자 신뢰성**이 정의되지 않았다. 할인율과 라벨 산식이 화면마다 다르면 서비스 신뢰가 바로 깨진다.

## E. v3(Opus 살붙이기)가 다룰 질문 5개

1. **상품 상세 기본 화면을 3블록으로 줄인다면 무엇을 남길 것인가?**  
   결론 카드 / 마트별 현재가 / 커뮤니티 검증을 기본으로 하고, 게이지·추이·도매가·표본은 “근거 자세히 보기”로 묶는 안을 검토하라.

2. **할인율 공식과 가격 용어를 한 장짜리 규칙으로 확정하라.**  
   `평소가(P50)`, `핫딜 기준가(P10)`, `지금 최저가`, `제보가`를 분리하고, 카드/상세/글쓰기에서 어떤 가격 기준으로 `-X%`를 표시할지 정하라.

3. **글쓰기 자동 등급 라벨의 출처 표시를 어떻게 할 것인가?**  
   `작성자 입력가 기준`, `공식몰 링크 확인`, `링크 없음`, `마트명/링크 불일치` 같은 배지를 글 상단에 어떤 우선순위로 보여줄지 정하라.

4. **비교 조합기는 빈 계산기인가, 프리셋형인가?**  
   초심자용으로 김치찌개/제육/샐러드 같은 프리셋을 먼저 제공하고, 핫딜러 모드에서 재료·수량·단위가를 조정하는 구조를 검토하라.

5. **v1에 넣을 최소 plugin/iframe 슬롯은 어디인가?**  
   상품 상세, 비교 조합기, 마이페이지 중 한 곳에 실제 동작하는 iframe 슬롯 1개를 만들고, 허용 URL/postMessage 이벤트를 최소 규격으로 정하라.
