# Web 영역 v1 초안 (Opus, Round-A)

> 라운드: A — 4영역(DB / 크롤러 / AI / 웹) 첫 기획 슬라이스
> 담당: Web (일반 사용자 프론트엔드 + Public/게시판 API)
> 범위: `packages/web-frontend/` 전체, `packages/web-api/backend/` 전체, 게시판 DB(`board.sqlite`)
> 비범위: 관리자 UI 3영역(db-admin / ai-admin / crawler-admin), 크롤러 코어, AI 학습 파이프라인, 상품 DB 스키마
> 작성자: Opus 4.7 (v1, "숲")
> 다음 단계: GPT-5.5 적대적 검토 → Opus 살붙임 → GPT 반론 → Opus 최종

## 0. TL;DR (30초 컷)

- **이 영역이 사용자 만족도의 90%를 결정한다.** 다른 영역이 아무리 정교해도 일반인이 첫 화면에서 "어, 쉽네"를 못 느끼면 끝.
- 사용자 인용: *"초심자도 이용하기 쉽게, 그러나 필요한 정보는 확실하게 한 눈에. 최소한의 노력으로 최대한의 효용을, 복잡하지 않게. 애초에 핫딜가는 찾아보면 누구나 찾을 수 있는데 복잡하고 귀찮아서 안 하는 겁니다. 우리는 가장 편리하고 가장 쉬워야 합니다."*
- 현 상태: 홈/검색/카테고리/상품상세/주유소/게시판(핫딜+자유)/회원가입·로그인/마이페이지가 **뼈대 수준으로 동작 중**. 다만 ① 첫 화면이 핫딜 그리드 한 덩어리뿐 — "왜 이게 핫딜인지" 한눈에 안 보임 ② 상품 상세에 **가격 추이 그래프 없음**, **도매가 라인 없음**, **마트 비교는 표뿐 가격 컬럼 없음** ③ 게시판 글쓰기에서 **본문 사이사이 이미지 삽입은 `[[img:0]]` 마커 수동 입력**으로만 가능 ④ **비교 조합기(식재료 vs 식당) 없음** ⑤ **식당(네이버 플레이스) 진입점 없음** ⑥ **모바일 분기 거의 없음** ⑦ **초심자/핫딜러 모드 토글 없음** ⑧ **알림 시스템 없음**.
- v1은 **숲**을 박는다: (a) 홈 3블록 구조(진짜 핫딜 TOP / 주변 핫딜 / 카테고리 진입), (b) 상품 상세 7블록(라벨/추이/마트표/도매가/적정가/관련 게시글/댓글), (c) 비교 조합기 페이지 신설, (d) 게시판 에디터의 인라인 이미지 + 상품 자동 매칭, (e) 초심자/핫딜러 모드 토글, (f) 식당 진입점 자리.
- **하지 않을 것**: v2/v3 미리 그리기, 다른 영역(DB/AI/크롤러) 내부, 안전·규격 타령으로 동적 기능 자르기.

## B. 사용자 관점 — 이 영역의 본질

> 사용자 명시 (원문): *"초심자도 이용하기 쉽게, 그러나 필요한 정보는 확실하게 한 눈에 들어오도록 제공할 수 있어야 하고 최소한의 노력으로 최대한의 효용을, 복잡하지 않게 얻을 수 있어야 합니다. 애초에 핫딜가는 찾아보면 누구나 찾을 수 있는데 복잡하고 귀찮아서 안 하는 겁니다. 우리는 가장 편리하고 가장 쉬워야 합니다."*

이 한 문장이 web 영역의 **헌법**이다. 모든 의사결정의 1차 필터:

1. **3초 룰** — 첫 화면 진입 후 3초 안에 "오늘 진짜 싼 거 뭐?"의 답 후보가 보여야 한다.
2. **2클릭 룰** — 어떤 상품이든 홈에서 2클릭 이내 상세까지 도달.
3. **0학습 룰** — 사용 설명 없이도 라벨만 보고 의미 추정 가능. (예: "🔥 핫딜", "🟢 저렴", "🟡 평소", "🔴 비쌈")
4. **양립 룰** — 초심자 화면을 최소화하면서, 핫딜러는 **토글 한 번**으로 P10/P25/P50/P75/분산/시즌보정/마트가중치를 즉시 본다.
5. **검증 가능 룰** — "이게 진짜 핫딜인가?"는 시스템이 단정하지 않고 **숫자 근거 + 사용자 토론(verdict)** 둘 다 제시.

핵심 정보 우선순위 (모든 페이지에 적용):
```
1순위: 가격 + 등급 라벨 (예: "₩1,980  🔥 핫딜")
2순위: 마트명 / 적정가 대비 (예: "이마트 · 평소보다 -32%")
3순위: 도매가 라인 / 시계열 / 표본 수 (핫딜러 모드에서 풀로)
4순위: 커뮤니티 검증 (댓글 verdict 집계 — "10명 중 8명: 진짜 핫딜")
```

인터랙션:

- 모바일: 카드 가로 스크롤 유지(swipe 자연스럽고 정보량은 줄지 않음).

## D. "초심자용" vs "핫딜러용" 양립

### D-1. 모드 정의

```
초심자 모드 (기본):
  - 가격 + 라벨 + 마트 + "평소 대비 -X%" 만 노출
  - 게이지는 5단계 색 칠한 막대
  - 표본 수 / sufficient 등 메타는 숨김
  - 단위가 정규화 OFF (포장 단위 그대로)

핫딜러 모드 (토글 ON):
  - P10/P25/P50/P75 4컬럼 노출
  - 표본 수 + sufficient 플래그
  - 마트 가중치 슬라이더 (균등 / 시장점유율 / 사용자 선호)
  - 배송비 포함 단위가 (g당 / ml당 / 1개당)
  - 시즌 보정 적용/해제
  - 다중 마트 추이 그래프
  - 도매가 라인 + 적정가 추정 박스
```

### D-2. 토글 위치

- 글로벌 NavBar 우상단 `[⚙ 핫딜러]` 토글 (localStorage).
- 모드 전환은 페이지 리로드 없이 즉시 — 상태는 `useContext` 또는 zustand 같은 가벼운 store. v1은 React Context 1개로 충분.

### D-3. 양립 원칙

- **데이터는 항상 풍부하게 fetch**, UI에서만 가린다. 토글로 즉시 노출.
- **카드 1장에 두 모드 정보 모두 슬롯**을 두고, CSS 클래스(`.pro-only`)로 보이기/숨기기. JSX 분기 최소화.

- **DB 제공 카테고리**: `board_category` 테이블 (현 코드 존재). 예: 핫딜 → 식료품/생활용품/가전/의류, 자유 → 일상/질문/정보.

### E-3. 글쓰기 UX (현 페이지 보강 포인트)

체크리스트:
- [ ] 이미지 업로드 후 "본문에 삽입" 버튼 → `[[img:N]]` 자동 삽입 (현 마커 방식 유지, UX만 개선)

## G. 플러그인 / iframe

### G-1. 페이지 컴포넌트 교체 슬롯

- React 라우트 `<Routes>`에서 페이지 컴포넌트를 **객체 맵**으로 분리: `{ home: HomePage, productDetail: ProductDetailPage, ... }`.
- 플러그인 등록 시 동일 인터페이스(props만 일치)면 교체 가능.
- v1에서 실제 플러그인 시스템은 안 짓지만, **컴포넌트 인터페이스를 props만 받는 순수 형태로 정리** — 향후 플러그인화의 전제 조건.

### G-2. iframe 격리

- 외부 URI/외부 API 위젯(예: 마트 공식 페이지 링크 미리보기)은 모두 `<iframe sandbox="allow-scripts">`로 격리.
- 사용자 커뮤니티 플러그인(예: 누군가 만든 "내 가계부 임포트" 위젯)도 iframe 격리, postMessage로 제한된 API만 노출.

### G-3. 이건 v1.5 ~ v2

v1에서는 자리(컴포넌트 인터페이스)만 잡고, 실제 plugin loader는 짓지 않는다.

## H. 모듈 / 결합도

### H-1. 영역 간 인터페이스

```
[web-frontend] ─HTTP─▶ [web-api/backend]
                            │
                            ├─SnapshotRepo (read-only sqlite, 공유 키 없음)
                            │
                            └─board.sqlite (글/댓글/이미지/신고/유저)
```

- web-frontend는 **web-api만** 호출. DB/AI/크롤러를 직접 호출하지 않음. ✅ (현 코드 준수)
- web-api는 **상품 DB는 read-only 스냅샷**으로만 접근. ✅ (`SnapshotRepo` 패턴 좋음)
- 게시판 DB는 별도 파일 (`board.sqlite`), 상품 DB와 **공유 외래키 없이** `canonical_id` 문자열로 약결합. ✅ (현 설계 유지)

### H-2. 결합 원칙 (재확인)

- ⚠ `Post.canonical_id`가 상품 DB의 캐노니컬과 어긋나도(스냅샷 빌드 직후 삭제된 ID 등) **게시글은 살아남고**, UI에서는 "매칭 상품 없음"으로 graceful fallback.
- ⚠ 상품 DB 재빌드 시 게시판 DB 무관 — 게시판은 자체 백업/마이그레이션.

### H-3. API 클라이언트 단일 게이트

- `packages/web-frontend/src/api/client.ts` 하나에 모든 fetch 집중. ✅ 유지.
- v1에서 추가할 함수: `fetchPriceHistory(canonical_id, mart?)`, `fetchRelatedPosts(canonical_id)`, `fetchFavorites()`, `addFavorite()`, `comparePresets()` 등. **단일 파일에 그룹 주석으로 섹션 분리**.

### J-2. 자기 의심

- **"가격 추이 그래프"가 정말 v1에 들어갈 수 있나?** — `price_observations` 시계열 있음, API 엔드포인트 신설(`GET /products/{id}/history?mart=&days=180`) + 가벼운 chart 라이브러리(recharts 등) 1개. v1 가능.
- **"도매가 라인"이 정말 v1?** — DB v1-opus에 "도매가 모델이 비어 있음"이 명시. v1에서는 **자리만 잡고 데이터 없으면 회색 박스**. UI는 늘 준비. ← 사용자 헌법 위반 아님(데이터 부재 ≠ UI 부재).
- **비교 조합기의 식당 데이터?** — 네이버 플레이스 API 결제/약관 미확정. v1은 **자리만**, 데이터 없으면 "주변 식당 평균 (준비 중)". 식재료 합산 자체는 v1 동작.
- **모바일 분기**가 v1 안에 들어갈 분량인가? — 인라인 style 점진 마이그레이션 + 미디어쿼리 4종 + 핵심 페이지만 손보면 1~2주 분량. 가능.
- **글로벌 CSS 도입이 인라인 style 일색인 현 코드와 충돌?** — 점진 마이그레이션 가능. 새 컴포넌트만 CSS 클래스, 기존은 그대로. 모순 없음.

### J-3. 위험 / 가지치기 후보

- 비교 조합기에서 사용자가 "조합 저장"을 게시판에 공유하면 게시판 글 모델 확장 필요(`compose_preset_json` 같은 필드). v1 보류, v1.5에서.
- 글쓰기 상품 자동완성은 좋은데, **사용자가 매칭 안 한 상품을 입력하면** "DB에 없는 상품"으로 표시 → 이게 escalation 큐로 흘러가는 결합점. DB 영역과 합의 필요.

## K. GPT-5.5가 봐야 할 포인트 (5개)

> Opus는 숲을 그렸다. GPT는 다음 5개를 **공격적으로 의심**해 달라.

1. **"상품 상세 7블록"이 진짜 일반 사용자에게 안 부담스러운가?**
   사용자 헌법은 "복잡하지 않게"인데, 라벨/게이지/추이/마트표/도매가/관련글/핫딜러까지 7개를 한 페이지에 쌓는 게 모순 아닌가? 초심자 모드에서는 추이/도매가/핫딜러 블록을 **기본 접힘**으로 두는 게 맞는가, 아예 안 보이는 게 맞는가? 어디까지가 "한 눈에"인가?

2. **"평소 대비 -X%"의 X 계산식이 정의되지 않았다.**
   `(P50 - 현재가) / P50` 인가, `(P25 - 현재가) / P25` 인가, 기간은 90일인가 6개월인가, 표본 부족 시 -X%는 어떻게 표시하는가? 이게 합의 안 되면 카드/상세/글쓰기 미리보기에서 **숫자가 서로 달라진다**. 사용자에게 가장 치명적 신뢰 손상 경로.

3. **글쓰기에서 "상품 자동완성 → canonical_id 자동 등록 → 등급 라벨 자동 표시"는 좋은데, 사용자가 일부러 다른 가격을 입력해 "🔥핫딜" 라벨을 만들 수 있다.**
   조작 가능성. verdict 댓글로 자정될까? 아니면 글 등록 전에 deal_url에 대해 자동 검증(공식 마트 페이지 fetch + 가격 파싱)이 필요한가? 이게 v1인가 v2인가?

4. **비교 조합기의 "식재료 vs 식당"이 v1에 정말 들어가야 하는가, 아니면 핵심 동선(검색→상세→게시판)에 집중하고 v1.5로 미루는 게 사용자 헌법에 더 부합하는가?**
   사용자 명시 요구지만, "최소한의 노력으로 최대한의 효용"이라는 헌법에 비추면 식재료 합산은 노력이 꽤 든다. 초심자가 진짜 쓸까? UX 검증 없이 v1에 넣는 게 맞는가?

5. **모바일 분기를 "글로벌 CSS 1장 + 미디어쿼리 4종"으로 처리하기엔 현 코드가 인라인 style 일색이라 일관성 깨질 위험.**
   v1에서 모바일 최적화를 진짜로 끝낼 수 있나, 아니면 핵심 3페이지(홈/검색/상품상세)만 모바일 완성하고 나머지는 v2로 미루는 게 정직한가? 부분 모바일 대응이 더 나쁜 결과(어떤 페이지는 되고 어떤 페이지는 안 되는)를 부르지 않는가?

## L. 본문 요약 (한 문단)

WalletSavior 웹(일반 사용자) 영역은 사용자 만족도의 90%를 짊어진다. 사용자 헌법은 "초심자에게 쉽고 핫딜러에게 충분, 최소 노력으로 최대 효용". 현 코드는 홈/검색/카테고리/상품상세/주유소/게시판/회원이 뼈대로 동작하나, ① 상품 상세에 가격 추이/도매가/마트 가격 컬럼이 없음 ② 게시판 글쓰기 인라인 이미지·상품 자동매칭 부재 ③ 비교 조합기·식당 페이지 자체 없음 ④ 초심자/핫딜러 모드 토글 없음 ⑤ 모바일 분기 거의 없음, 이 5개가 핵심 공백. v1은 (a) 홈 3블록, (b) 상품 상세 7블록(추이/도매가/마트표 가격 컬럼/관련 게시글 추가), (c) 비교 조합기 페이지, (d) 글쓰기 인라인 이미지·상품 자동완성·실시간 등급 미리보기, (e) 초심자/핫딜러 글로벌 토글, (f) 즐겨찾기·마이페이지, (g) 모바일 미디어쿼리 4종을 박는다. 식당·알림·소셜로그인·플러그인 시스템은 자리만 잡고 v1.5/v2로 미룬다. 결합도는 web→api, api→상품DB(read-only), 게시판DB(별도)의 3층을 유지하며 plugin/iframe 자리는 컴포넌트 인터페이스 정리 수준에서 멈춘다.
