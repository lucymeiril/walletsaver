# Web 영역 v4 반론 (GPT-5.5, Round-A)

> 입력: `docs/planning/round-A/web-v1-opus.md`, `web-v2-gpt.md`, `web-v3-opus.md`  
> 출력: `docs/planning/round-A/web-v4-gpt.md`  
> 역할: v3에 굴복하지 않고, v2의 약점도 다시 의심하는 반론자.  
> 원칙: 기능을 봉인하지 않는다. 모드 토글·플러그인·외부 이미지·자유 입력은 살린다. 대신 숫자, 흐름, 화면, 엣지를 더 세게 깐다.

---

## A. 본문 요약 + 내 입장

v1은 웹 영역의 큰 그림을 잡았다. 홈은 핫딜 TOP/주변/카테고리/게시글로 바꾸고, 상품 상세는 라벨·게이지·추이·마트표·도매가·관련글·핫딜러 패널을 얹고, 게시판은 인라인 이미지·상품 자동매칭·실시간 등급을 붙이고, 비교 조합기와 모드 토글까지 넣자는 안이다.

v2는 이 안을 찔렀다. `/fuels` 라우트 누락, autocomplete 파라미터 오류, `PriceGauge currentPrice=p50`, P10을 현재 핫딜가처럼 보이게 만드는 문제, `평소 대비 -X%` 산식 미정의, 글쓰기 등급 조작 가능성, 즐겨찾기/재방문 동기 부족, 플러그인 슬롯 약함을 잡았다. 이 중 상당수는 실제 코드와 맞다.

v3는 v2 중 사실 오류와 숫자 신뢰 문제는 받아들이고, v2의 축소·봉인 성향은 밀어냈다. 상품 상세 7블록은 유지하되 3계층으로 접고, 산식은 하나로 고정하고, 글쓰기에는 3종 신뢰 배지를 붙이고, 비교 조합기는 프리셋+자유 추가로 두고, iframe 슬롯 2개를 v1에 넣었다.

내 입장: v3의 방향은 v2보다 사용자 의도에 더 맞다. 특히 7블록 제거, 플러그인 봉인, 외부 이미지 렌더 거부, 글쓰기 가격 입력 제한 같은 식으로 사용자를 좁히면 WalletSavior의 기획 맛이 죽는다. 하지만 v3는 “살리겠다”에 집중하다가 실제 사용 장면의 마찰을 덜 팠다. 3계층은 검증 전 가정이고, 통일 산식은 데이터가 빈약한 상품에서 흔들리고, 신뢰 배지는 많아지면 못 읽히고, iframe 슬롯 2개는 위치만 있고 용도가 흐리며, 자유 카테고리는 정형 카테고리와 충돌한다. v5는 이 다섯 군데를 결단해야 한다.

## B. v3가 v2를 배척한 항목 재검토

### 1. “상품 상세 7블록 → 3블록 축소” 배척

v3의 배척은 절반은 맞다. 정보를 아예 없애면 핫딜러가 쓸 이유가 줄고, 사용자가 원한 “필요한 정보는 확실하게”도 약해진다. 문제는 v3가 7블록을 살리는 근거로 “접힘/모드면 된다”를 너무 쉽게 썼다는 점이다.

구체 시나리오:

- 모바일에서 상품 상세 진입.
- 항상 펼침 3블록: 결론 라벨, 마트별 가격표, 관련 게시글.
- 하단 액션바: 즐겨찾기/알림/글쓰기/조합 추가.
- 접힘 헤더 4개: 게이지, 추이, 도매가, 핫딜러 패널.

이 화면은 “7블록을 다 보여준 것”은 아니지만, 초심자에게는 여전히 선택지가 많다. 특히 관련 게시글이 항상 펼침이면 가격 확인보다 커뮤니티 노이즈가 먼저 들어올 수 있다. `마트별 가격표`가 길면 관련글과 액션바가 아래로 밀린다.

결론: 7블록 유지 자체는 정당하다. 다만 항상 펼침 3개가 정답이라는 보장은 없다. `관련 게시글`은 상품에 따라 항상 펼침이 아니라 “검증 요약 1줄 + 펼침”이 나을 수 있다. v5는 7블록 유지와 항상 펼침 구성을 분리해서 결정해야 한다.

### 2. “회색 자리표시 블록 여러 개 두지 마라” 배척

v3는 도매가처럼 데이터가 없으면 헤더 자체를 숨긴다고 보강했다. 이건 v2보다 낫다. 다만 “자리부터 잡아야 나중에 생긴다”는 v3 논리는 모든 블록에 적용하면 위험하다.

구체 시나리오:

- 가격 추이 API가 아직 없다.
- 현재가 API도 없다.
- 도매가 모델도 없다.
- 식당 데이터도 없다.
- 플러그인 슬롯도 빈다.

이때 화면 곳곳에 “준비 중”이 보이면 사용자는 기능이 많은 서비스가 아니라 덜 만든 서비스로 본다. v3가 슬롯 비어 있으면 플러그인 자리는 숨기겠다고 한 건 맞는 방향이다. 같은 원칙을 도매가, 식당 평균, 알림 발송에도 적용해야 한다.

결론: v3 배척은 부분 정당. “미래 자리”는 관리자·기획 문서에 존재하면 되고, 사용자 화면에는 데이터나 동작이 있는 순간부터 보이는 게 맞다.

### 3. “이미지 10장·5MB 상한” 배척

v3의 배척은 정당하다. 숫자를 지금 박을 근거가 없다. 다만 “운영 단계 파라미터”라고만 두면 구현자가 업로드 제한을 어디에도 안 만들 수 있다.

구체 시나리오:

- 사용자가 모바일에서 사진 20장을 올린다.
- 업로드는 오래 걸리고, 실패하면 어떤 파일이 실패했는지 모른다.
- 글쓰기 화면은 본문 마커와 이미지 순서가 어긋난다.

여기서 필요한 건 임의 숫자 고정이 아니라 UX 규칙이다.

- 선택한 이미지 총 용량/개수 표시.
- 업로드 진행률 표시.
- 실패한 이미지 재시도.
- `[[img:N]]`의 N이 재정렬되어도 깨지지 않도록 이미지 ID 기반 마커 검토.

결론: v3처럼 숫자 고정은 피하되, 업로드 흐름의 실패 상태는 v1 설계에 들어가야 한다.

### 4. “외부 이미지 URL을 링크로만 표시” 배척

v3의 배척은 맞다. 외부 이미지 자체를 안 보이게 하면 게시판 자유도가 급감한다. 그러나 “외부 배지면 충분”은 아직 얇다.

구체 시나리오:

- 쇼핑몰 할인 캡처를 외부 이미지로 올린 글이 인기글이 된다.
- 2주 후 외부 호스팅 이미지가 삭제된다.
- 본문은 `가격표 보세요`인데 이미지는 깨져 있다.

이건 차단 문제가 아니라 보존 문제다. 외부 이미지를 렌더하되, 깨졌을 때 대체 UI가 필요하다.

- 이미지 로드 실패 시 `이미지가 사라졌습니다 · 원문 링크 보기` 표시.
- 작성자가 외부 이미지에 짧은 설명을 붙일 수 있게 한다.
- 인기글/핫딜글은 외부 이미지가 깨졌을 때 작성자에게 수정 유도 알림을 보낸다.

결론: v3 배척은 정당. 하지만 외부 이미지의 링크 깨짐 대응을 추가해야 한다.

### 5. “글 등록 전 deal_url fetch + 가격 파싱 의무화” 배척

v3의 배척은 정당하다. 마트별 파서를 v1 의무로 만들면 글쓰기 흐름이 느려지고, 파싱 실패가 글 등록 실패로 번진다. 다만 “verdict 댓글이 자정”이라는 v3의 근거는 초반 트래픽이 적을 때 약하다.

구체 시나리오:

- 초기 서비스라 댓글이 거의 없다.
- 사용자가 `제보가 100원`으로 올린 글이 홈 인기 핫딜에 노출된다.
- `작성자 입력가 기준` 배지가 작으면 카드에서는 과장 라벨만 남는다.

해결은 등록 차단이 아니다. 노출 순위와 라벨 강도를 다르게 해야 한다.

- 링크 없음/외부 링크/마트 불일치 글은 홈 TOP 노출에서 감점.
- `작성자 입력가 기준`은 글 상세의 작은 보조문구가 아니라 카드에도 붙인다.
- 댓글 수가 적은 글은 `검증 중` 상태를 카드에 같이 표시한다.

결론: 파싱 의무화 거부는 맞다. 대신 검증 약한 글이 홈 최상단을 먹는 문제는 v3가 덜 봤다.

### 6. “OAuth vs 자체 가입 재검토 / 비밀번호 재설정 우선” 배척

v3는 “v1=자체 유지”로 못박았다. 결단 자체는 좋다. 그러나 자체 로그인을 유지하면 로그인 세션 만료, 비밀번호 분실, 이메일 오타가 바로 UX 문제가 된다.

구체 시나리오:

- 사용자가 긴 핫딜 글을 작성 중이다.
- 세션이 만료된다.
- 등록 버튼을 누르자 401이 나고 본문이 날아간다.

이건 소셜 로그인 우선순위 문제가 아니라 글쓰기 보존 문제다. v1에 필요한 건 다음이다.

- 401 발생 시 로그인 모달을 띄우고, 작성 중 폼은 유지.
- 글쓰기 draft를 localStorage에 자동 저장.
- 세션 만료 안내는 페이지 이동 없이 처리.

결론: v3의 “자체 유지” 결단은 유지. 대신 세션 만료 UX는 P0로 올려야 한다.

### 7. “핫딜러 기능 단계화” 배척/부분수용

v3는 모드 자체는 v1, 고급 기능은 단계화로 정리했다. 이건 맞다. 하지만 “항상 풍부하게 fetch하고 UI에서만 가림”은 검색 성능과 모바일 데이터 사용량에서 문제가 된다.

구체 시나리오:

- 상품 1만 개 이상, 검색 결과 20개.
- 각 카드가 P10/P50, 단위가, 표본, 마트별 현가, 추이 미니데이터까지 항상 받는다.
- 초심자 모드에서는 대부분 숨긴다.

숨길 데이터를 매번 받으면 검색이 느려진다. 모드 토글은 유지하되 API 응답은 가벼운 카드 응답과 상세 응답을 분리해야 한다.

결론: 모드 유지 정당. “항상 풍부하게 fetch”는 재검토.

### 8. “플러그인 허용 URL/postMessage 사전 규격 강제” 배척

v3는 슬롯을 열고 설정 파일로 운영자가 채우게 했다. 사용자 자체 개조 취지에는 맞다. 하지만 postMessage 이벤트를 `resize`, `navigate` 2개로 못박으면서도 슬롯 용도를 정하지 않았다.

구체 시나리오:

- 상품 상세 하단 슬롯에는 외부 가격 계산기를 넣고 싶다.
- 마이페이지 슬롯에는 가계부 위젯을 넣고 싶다.
- 둘 다 필요한 입력 데이터가 다르다. 상품 슬롯은 canonical_id, 상품명, 현재가가 필요하고, 마이페이지 슬롯은 사용자 즐겨찾기/최근 본 상품 요약이 필요하다.

이벤트 2개보다 먼저 필요한 건 슬롯별 컨텍스트 계약이다. `resize/navigate`만 있으면 위젯은 껍데기만 뜨고 WalletSavior 데이터와 연결되지 않는다.

결론: v3의 슬롯 v1 진입은 맞다. 위치별 데이터 전달 범위를 정하지 않은 게 약점이다.

## C. v3가 새로 도입한 것의 약점

### C-1. 3계층(항상펼침3/접힘4/모드별) UX 검증 부재

v3는 상품 상세를 다음으로 나눴다.

- 항상 펼침: 결론 라벨, 마트별 가격표, 관련 핫딜 게시글.
- 접힘 기본: 게이지, 추이, 도매가/적정가, 핫딜러 패널.
- 핫딜러 모드: 게이지/추이/패널 펼침.

이 구조는 그럴듯하지만 검증된 건 아니다. 특히 항상 펼침 3개 중 `관련 게시글`이 문제다. 사용자가 상품 상세에 온 1차 목적은 “어디서 얼마에 살 수 있나”다. 관련글 3건이 항상 펼쳐지면 가격표 아래 공간을 크게 먹고, 댓글 싸움이 가격 결정보다 먼저 보일 수 있다.

대안:

- 항상 펼침은 `결론 라벨 + 구매 가능한 가격 카드/표 + 검증 요약 1줄`로 줄인다.
- 관련글 3건은 `검증 요약 1줄`을 누르면 펼친다.
- 핫딜러 모드에서도 관련글보다 추이/표본을 먼저 펼친다.
- 모바일에서는 마트표가 3개 초과일 때 첫 3개만 보이고 `전체 보기`로 확장한다.

핵심은 7블록을 없애는 게 아니라 “항상 펼침 3개”의 멤버를 다시 고르는 것이다.

### C-2. “평소 대비 -X%” 통일 산식의 엣지

v3 산식:

```text
discount_pct = (P50 - 표시가격) / P50 × 100
표본 < 10건 → 숨김
P50 누락 → 숨김
```

이 산식은 기본값으로는 좋다. 하지만 다음 상품에서 흔들린다.

#### 1) 거래량 적은 상품

월 2~3번만 관측되는 상품은 90일 P50이 낡은 가격일 수 있다. 표본 10건을 넘겨도 계절/행사/마트 변경으로 기준이 왜곡된다.

- 예: 수입 치즈, 특정 브랜드 소스, 지역 한정 상품.
- `표본 12건`이지만 6건은 80일 전, 6건은 최근 7일.
- P50은 과거 가격에 끌려 현재 할인율이 과장된다.

보강: 표본 수뿐 아니라 `최근성`을 같이 본다. `최근 30일 관측 N건`, `마지막 관측 D일 전`을 할인율 표시 조건에 넣어야 한다.

#### 2) 신상품

신상품은 P50이 없다. v3는 할인율을 숨긴다. 그러면 신상품 핫딜 제보는 “가격만 있는 글”이 되어 게시판에서 매력이 약해진다.

보강:

- 동일 카테고리/용량 유사 상품의 범위를 참고한 `카테고리 기준 참고가`를 별도 라벨로 표시.
- 단, 이것은 `평소 대비`가 아니라 `유사상품 대비`로 라벨을 다르게 박는다.

#### 3) 단종/리뉴얼 상품

단종 직전 떨이 가격은 P50 대비 크게 싸다. 하지만 다시 살 수 없는 상품이면 홈 TOP을 먹어도 재방문 가치가 낮다.

보강:

- `최근 7일 구매 가능 링크 수`가 0이면 홈 TOP 제외 또는 `재고 불확실` 표시.
- 상품명 리뉴얼/용량 변경 감지 시 이전 P50을 그대로 쓰지 않는다.

#### 4) 용량 변경 상품

`300g → 270g` 리뉴얼은 가격만 보면 싸 보일 수 있다. v3는 단위가를 핫딜러 쪽에 둔다. 그러나 용량 변경은 초심자에게도 바로 영향을 준다.

보강:

- 카드/상세 결론에 `단위가 변동` 경고가 필요하다.
- 용량 파싱 실패 상품은 할인율 신뢰도를 낮춘다.

### C-3. 자동완성 신뢰 배지 3종이 인지 과부하인가

v3의 글쓰기/글상단 배지:

- 공식몰 링크 확인됨
- 링크 없음/링크 외부
- 마트명/링크 불일치
- 라벨 옆 `작성자 입력가 기준`

방향은 맞다. 문제는 배지가 라벨, verdict, 카테고리, 가격, 마트명과 한 줄에 겹치면 못 읽힌다는 점이다.

구체 시나리오:

```text
🔥 핫딜 (작성자 입력가 기준) 🟡 링크 외부 #한우 #이마트 💬12 🔥8 ❌2
```

초심자는 어디를 봐야 할지 모른다. 배지가 많아질수록 “이 글을 믿어도 되나?”보다 “뭔가 복잡하다”가 먼저 온다.

대안:

- 카드에서는 배지 1개만 노출: `검증됨 / 검증중 / 불일치`.
- 상세에서만 세부 사유 3종을 펼친다.
- `작성자 입력가 기준`은 항상 노출하되 짧게 `제보가 기준`으로 통일.
- verdict 집계와 링크 신뢰 배지를 분리한다. 링크 배지는 가격 출처, verdict는 커뮤니티 판단이다.

### C-4. iframe 슬롯 2개 위치/크기 결정 부족

v3는 상품 상세 하단 + 마이페이지 사이드 2슬롯을 제안했다. 위치만 있고 크기·용도·빈 상태·모바일 배치가 덜 정해졌다.

문제 시나리오:

- 상품 상세 하단 iframe이 높이 600px로 열리면 관련글/액션 이후 페이지가 길어진다.
- 마이페이지 사이드는 모바일에서 사이드가 사라진다. 그러면 슬롯도 사라지는가, 아래로 내려가는가?
- 외부 위젯이 느리면 전체 상세 페이지가 늦게 보이는 것처럼 느껴진다.

보강:

- 상품 상세 슬롯: 기본 접힘 카드로 시작. `외부 계산기 열기` 클릭 시 lazy load.
- 마이페이지 슬롯: PC는 우측, 모바일은 즐겨찾기 아래 접힘 영역.
- iframe 최대 기본 높이와 resize 상한 필요. 예: 기본 320px, 사용자 펼침 시 확장.
- 위젯 로딩 지연 시 skeleton이 아니라 `외부 위젯 불러오는 중` 별도 placeholder를 둔다.
- 슬롯별 컨텍스트를 정의한다.
  - 상품 슬롯: canonical_id, product_name, displayed_price, p50, grade.
  - account 슬롯: favorite_count, recent_count 정도의 요약. 개인 상세 데이터는 위젯에 자동으로 던지지 않는다. 필요한 경우 사용자가 직접 연결.

### C-5. 자유 카테고리 임의 지정 + 정형 카테고리 충돌

v3는 `board_category`와 `freeform_category` 병존을 유지하고, 자유 태그 필터 API를 추가했다. 방향은 좋다. 문제는 둘이 충돌할 때 화면 기준이 없다.

구체 시나리오:

- 정형 카테고리: `식료품 > 육류`
- 자유 카테고리: `#의류`
- 제목: “한우 등심”

또는:

- 정형 카테고리: `의류`
- 자유 카테고리: `#한우 #이마트`

검색/필터/추천에서 어느 쪽을 믿을지가 없다.

보강:

- 정형 카테고리는 탐색/정렬의 기준.
- 자유 카테고리는 발견/묶음의 기준.
- 목록 카드에는 둘 다 보이되 시각 계층을 다르게 한다. 정형은 칩 1개, 자유는 해시태그.
- 충돌이 심한 글은 자동 차단하지 말고 `카테고리 수정 제안` 버튼을 둔다.
- 글쓰기에서 상품 자동매칭이 되면 정형 카테고리 후보를 제안하되, 사용자가 바꿀 수 있게 한다.

## D. v3 자수 6포인트 보강

v3가 스스로 “v4가 깔만한 약점”으로 적은 6개를 더 세게 보강한다.

### 1. 현재가 API의 “최근 7일” 윈도우

7일은 모든 상품에 맞지 않는다. 계란/우유처럼 자주 관측되는 상품은 7일이 충분하지만, 수입 식재료·의류·가전은 7일이면 관측이 0일 수 있다.

보강안:

- 상품별 관측 빈도에 따라 윈도우를 자동 확장한다: 7일 → 14일 → 30일.
- 화면 라벨은 `최근 7일 최저가`, `최근 30일 확인가`처럼 실제 윈도우를 표시한다.
- 홈 TOP은 윈도우가 30일까지 확장된 상품을 감점한다. 너무 오래된 가격이 TOP을 먹으면 안 된다.

### 2. 신뢰 배지 화이트리스트 운영 비용

`mart_aliases.mart_url_domain`을 쓰면 시작은 쉽다. 하지만 도메인 하나로 마트와 판매자를 구분하기 어렵다.

예:

- 오픈마켓 도메인 안에 공식 판매자와 일반 판매자가 섞임.
- 모바일 도메인, 단축 URL, 제휴 URL이 섞임.
- 같은 마트의 이벤트 서브도메인이 다름.

보강안:

- 도메인 매칭 결과를 4단계로 둔다: `공식몰`, `동일 플랫폼`, `외부`, `불일치`.
- 작성자가 링크를 붙이면 미리보기에서 판정 결과를 즉시 보여준다.
- 운영자가 도메인 매칭을 수정할 수 있는 작은 관리 화면이 필요하다. JSON만 편집하는 방식은 초반엔 되지만 누적되면 실수한다.

### 3. 비교 조합기 프리셋 6개의 근거

김치찌개/된장찌개/제육/샐러드/카레/파스타는 무난하지만 근거가 없다. 중요한 건 메뉴명이 아니라 “검색에서 바로 조합으로 이어지는가”다.

보강안:

- 프리셋은 고정 6개가 아니라 홈 검색 로그/게시판 언급량 기준으로 재정렬.
- 첫 버전은 6개를 박되, 카드 하단에 `자주 찾는 조합` 영역을 따로 둔다.
- 프리셋마다 기본 인분, 재료 용량, 대체 재료를 명시한다.
- `김치찌개`를 골랐는데 사용자가 두부를 빼거나 돼지고기를 바꾸는 흐름이 쉬워야 한다.

### 4. iframe 슬롯 2개의 실제 후보 불명

v3는 후보를 P1로 미뤘다. 그러면 v1 슬롯은 빈 껍데기일 수 있다.

보강안:

- v1에서 슬롯 2개를 넣으려면 최소 1개 샘플 위젯을 같이 넣어야 한다.
- 상품 상세 슬롯 샘플: `단위가 계산기` 또는 `장바구니 메모 위젯`.
- 마이페이지 슬롯 샘플: `이번 주 찜 상품 가격 요약`.
- 외부 플러그인까지 기다리지 말고, 내부 샘플 iframe으로 슬롯 크기/resize/navigate를 검증한다.

### 5. 모바일 공통 컴포넌트 5종의 디자인 사양 부족

패턴만 있고 실제 기준값이 부족하다. 구현자는 매번 다르게 만든다.

보강안:

- 카드 최소 터치 영역 44px.
- 하단 액션바 높이, 접힘 헤더 높이, 필터 바텀시트 최대 높이를 정한다.
- 마트표 카드 변환 규칙: 핵심 4필드만 첫 화면, 나머지는 펼침.
- 모바일 자동완성은 화면 전체 오버레이로 열고, 한국어 IME 조합 중 Enter 처리 예외를 둔다.

### 6. 자유 카테고리 필터 API가 백엔드 변경을 동반

web-api 범위라서 침범은 아니다. 문제는 API 하나 추가로 끝나지 않는다는 점이다.

보강안:

- `freeform` 정확일치, 부분일치, 대소문자/공백 정규화 기준을 정한다.
- 여러 태그를 허용할지, 단일 문자열만 둘지 결정한다.
- 지금 `freeform_category` 단일 필드라면 `#한우 #이마트`를 하나의 문자열로 저장할 가능성이 있다. 필터가 망가진다.
- v1에서 진짜 태그처럼 쓰려면 `PostTag(post_id, tag)` 테이블이 더 맞다. 단, 빠른 시작은 단일 freeform 유지 + 쉼표/공백 파싱 규칙 명시.

## E. v1~v3 모두 놓친 시나리오

### 1. 검색 성능: 상품 1만+일 때

현재 `search_products`는 서비스 레이어에서 리스트를 필터/정렬하고 페이지 슬라이스한다. 상품이 1만 개를 넘으면 정렬·필터·자동완성이 동시에 느려질 수 있다. 특히 홈, 검색, 카테고리, 자동완성이 같은 인덱스를 두드리면 체감이 바로 나빠진다.

필요한 결정:

- 검색 결과 API는 카드용 경량 필드만 반환.
- 상세 데이터는 상세 진입 시 별도 호출.
- autocomplete는 prefix 인덱스를 별도 유지하고, 응답 10개 제한을 지킨다.
- 정렬 `hot_deal`은 매 요청 계산이 아니라 스냅샷 빌드 시 점수 캐시를 고려한다.
- 검색 결과 로딩은 300ms 이상이면 skeleton 카드 표시.

### 2. 무한 스크롤 vs 페이지네이션

v1/v3는 카테고리 와이어에 페이지 번호를 그렸다. 모바일에서는 페이지네이션보다 더보기/무한 스크롤이 자연스럽다. 게시판은 반대로 무한 스크롤만 쓰면 사용자가 이전 위치를 잃는다.

결정안:

- 상품 검색/카테고리: 모바일 `더보기`, PC 페이지네이션 또는 더보기.
- 게시판: 페이지네이션 유지 + 정렬/검색 상태 URL 보존.
- 홈 TOP: 고정 12개, 더보기는 검색 결과로 이동.
- 뒤로가기 시 스크롤 위치 복원.

### 3. SEO/메타: 가격 정보가 검색 노출에 미치는 영향

상품 상세와 게시글은 검색엔진에 노출될 수 있다. 가격 정보가 메타에 들어가면 클릭률이 오를 수 있지만, 가격이 자주 바뀌면 오래된 스니펫이 생긴다.

필요한 것:

- 상품 상세 title: `상품명 - 지금 최저가/평소가 | WalletSavior`.
- description에는 `최근 확인일` 포함.
- 게시글 title은 사용자 제목 + 가격 + 마트.
- 가격이 오래됐으면 메타에 `최근 확인일`을 강조.
- canonical URL 정책: `/p/:canonical_id`, `/post/:id` 고정.

### 4. 웹 푸시 권한 흐름

v3는 알림 입력 UI 저장만 v1, 발송은 v1.5로 뒀다. 그래도 웹 푸시 권한 요청 흐름은 미리 설계해야 한다. 브라우저 권한 팝업을 너무 빨리 띄우면 거부율이 높다.

결정안:

- 상품 상세에서 `₩X 이하 알림` 저장 버튼을 누른 뒤에만 권한 요청.
- 비로그인은 로컬 알림 희망가 저장 → 로그인 후 서버 동기화 제안.
- 권한 거부 시 다시 누르면 브라우저 설정 안내.
- NavBar 종 아이콘은 `알림함`과 `권한 상태`를 분리해서 보여준다.

### 5. 회원/비회원 차이 + 게스트 즐겨찾기

v3는 비로그인 즐겨찾기를 localStorage로 둔다. 좋다. 빠진 건 로그인 전환 시 병합이다.

시나리오:

- 비로그인으로 상품 12개 찜.
- 회원가입.
- 서버 즐겨찾기와 로컬 즐겨찾기가 충돌.

결정안:

- 첫 로그인 후 `기기 즐겨찾기 12개를 계정에 합칠까요?` 모달.
- 중복은 자동 병합.
- 사용자가 거절하면 localStorage는 유지하되 서버와 분리.
- 게스트 최근 본 상품도 같은 방식으로 병합 가능.

### 6. 모바일 PWA 가능성

가격 알림, 재방문, 홈 화면 바로가기를 생각하면 PWA가 어울린다. v1에 본격 PWA를 넣지 않아도 manifest 방향은 잡아야 한다.

필요한 것:

- 앱 이름/아이콘/테마 색.
- 오프라인일 때 최소 fallback: `최근 본 상품`, `찜한 상품` 로컬 캐시.
- 설치 유도는 과하게 띄우지 말고 마이페이지나 즐겨찾기 탭에서만.

### 7. 다크모드 가격 색감 + 색맹 접근성

v3는 CSS 토큰과 이모지를 언급했다. 부족하다. 녹색/빨강 가격 라벨은 색맹 사용자에게 약하다. 다크모드에서는 빨강이 더 공격적으로 보일 수 있다.

결정안:

- 라벨은 색 + 아이콘 + 텍스트를 동시에 사용.
- `🔥 핫딜`, `↓ 저렴`, `— 평소`, `↑ 비쌈`처럼 방향 기호 추가.
- 다크모드 색은 단순 반전이 아니라 대비 테스트 필요.
- 차트 선은 색만 다르게 하지 말고 점선/실선 패턴도 다르게.

### 8. 게시판 검색/태그 정렬

v1/v3는 게시판 검색과 태그 필터를 말하지만 정렬 기준이 약하다.

필요한 정렬:

- 최신순.
- 댓글 많은 순.
- verdict 핫딜 비율순.
- 제보가 할인율순.
- 링크 검증됨 우선.
- 태그 클릭 시 해당 태그 내에서도 위 정렬 유지.

게시판 검색은 제목/본문만이 아니라 마트명, deal_url 도메인, freeform tag, canonical 상품명까지 걸려야 한다.

### 9. 신고/모더레이션 흐름 구체화

v3는 신고 사유 드롭다운과 admin 큐를 말한다. 빠진 건 신고 후 사용자 피드백이다.

필요한 흐름:

- 신고 클릭 → 사유 선택/입력 → 완료 후 `신고 접수됨`.
- 같은 사용자가 같은 대상 중복 신고하면 기존 신고 업데이트 또는 안내.
- 신고한 글이 처리되면 알림함에 `처리됨/반려됨` 표시.
- 모더레이터가 숨김 처리한 글은 작성자에게 이유를 보여준다.
- 허위 핫딜 신고는 가격/링크 배지와 연결해 처리 큐에서 우선순위 상승.

### 10. 인라인 이미지 외부 호스팅 — 이미지 사라짐 대응

C에서 말한 것처럼 외부 이미지는 깨진다. v1~v3는 렌더 여부만 봤고, 사라진 뒤 본문이 망가지는 문제를 덜 봤다.

결정안:

- 이미지 `onError` UI 필수.
- 외부 이미지 alt/설명 입력 권장.
- 인기글의 외부 이미지가 깨지면 작성자에게 수정 요청.
- 깨진 이미지가 가격 증빙의 핵심이면 글 카드에 `이미지 증빙 사라짐` 표시.

### 11. 댓글 알림/멘션

알림은 가격만이 아니다. 커뮤니티가 있으면 댓글/답글/멘션 알림이 재방문 핵심이다.

필요한 것:

- 내 글 댓글 알림.
- 내 댓글에 답글 알림. 현재 댓글이 flat 구조면 답글 기능을 v1.5로 둘지 결정.
- `@닉네임` 멘션 파싱.
- 알림함에서 읽음 처리.
- 알림 이메일은 보류 가능하지만 웹 알림함은 필요하다.

### 12. 사이트 전체 로딩 지연 시 placeholder UX

현재 일부 페이지는 `로딩 중...` 텍스트다. 기능이 늘면 이걸로 부족하다.

결정안:

- 홈: 핫딜 카드 skeleton.
- 검색: 결과 카드 skeleton + 검색어 유지.
- 상품 상세: 제목/가격/표 skeleton.
- 게시판: 리스트 skeleton.
- iframe: 외부 위젯 placeholder 별도.
- API 오류 시 재시도 버튼과 이전 데이터 유지.

### 13. 로그인 세션 만료 UX

B에서도 말했지만 중요하다. 글쓰기/댓글/즐겨찾기/알림 저장 중 401이 나면 작업이 날아가면 안 된다.

결정안:

- 모든 mutation에서 401 공통 처리.
- 로그인 모달 후 원래 요청 재시도.
- 글쓰기 draft 자동 저장.
- 댓글 입력값 유지.
- 즐겨찾기 클릭은 비로그인 localStorage로 fallback.

### 14. 한국어 IME 입력기 호환

자동완성, 검색, 태그 입력, 댓글에서 한국어 조합 중 Enter가 문제를 만든다.

시나리오:

- 사용자가 `두부`를 입력 중 조합 확정 Enter를 누른다.
- 폼 submit이 먼저 발생한다.
- 자동완성 선택/검색 실행이 꼬인다.

결정안:

- `compositionstart/compositionend` 상태를 SearchBar, 태그 입력, 댓글 입력에 적용.
- 조합 중 Enter는 submit으로 처리하지 않는다.
- 자동완성 debounce는 조합 종료 후 실행.
- 초성 검색(`ㄷㅂ`)과 완성형 검색(`두부`) 결과 차이를 테스트한다.

## F. v5(Opus 최종)가 결단할 질문 5개

1. **상품 상세 항상 펼침 3블록을 그대로 둘 것인가?**  
   내 제안: `결론 라벨 + 구매 가능 가격 + 검증 요약 1줄`로 재편. 관련글 3건은 기본 접힘.

2. **할인율 표시 조건을 표본 수만 볼 것인가, 최근성/구매 가능성/용량 변경까지 볼 것인가?**  
   내 제안: `표본 수 + 마지막 관측일 + 최근 링크 수 + 용량 신뢰도`를 같이 본다.

3. **글쓰기 신뢰 배지는 카드에서 몇 개까지 보여줄 것인가?**  
   내 제안: 카드 1개(`검증됨/검증중/불일치`), 상세에서 세부 배지 펼침.

4. **iframe 슬롯 2개를 v1에 넣는다면 샘플 위젯까지 넣을 것인가?**  
   내 제안: 최소 내부 샘플 iframe 1개를 넣어 크기/resize/모바일 배치를 검증한다.

5. **검색/게시판 목록은 페이지네이션, 더보기, 무한 스크롤 중 무엇을 쓸 것인가?**  
   내 제안: 상품 모바일은 더보기, PC는 페이지/더보기 혼합, 게시판은 페이지네이션 + URL 상태 보존.

## 마지막 판단

v3의 큰 방향은 유지할 만하다. 사용자가 원한 건 기능을 접고 봉인하는 웹이 아니라, 자유 입력·핫딜러 모드·플러그인·커뮤니티 검증이 살아 있는 웹이다. 다만 v3는 “살리는 결단” 뒤의 작은 마찰을 덜 팠다. v5는 기능을 줄이는 쪽이 아니라, 노출 우선순위·데이터 신뢰 조건·느린 로딩·한국어 입력·게스트 전환·링크 깨짐 같은 실제 사용 장면을 박아야 한다.
